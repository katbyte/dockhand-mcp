# api-defs

How the Dockhand API document is fetched, the definitions imported from it, and what the server does that the document does not say.

## The document

**Where it comes from:** a running Dockhand. **What is committed:** the pin, the definitions and the generated client. **What is not:** the document.

Dockhand describes its HTTP API in an OpenAPI document that every running server serves about itself at `/openapi.json`, with or without a login. That served document is the one source of the definitions and the client, and it is not kept in this repository. `api-defs/get.sh` starts a throwaway server of the published image (`fnsys/dockhand`), asks it for `/openapi.json` and removes it again; nothing is taken from Dockhand's source repository. The document is saved as `dockhand-openapi-<version>.json`, named for the server version it describes, and holds it to the checksum in `dockhand-openapi.pin`; git ignores the file. It is a build input: [pandorest](https://github.com/katbyte/pandorest) imports it into the definitions under `dockhand-<version>/` beside it, fixing what it gets wrong with named workarounds on the way (`sdk/pandorest/workarounds`), and generates `sdk/dockhand` from those definitions.

| File | Source | Version |
|---|---|---|
| `dockhand-openapi.pin` | written by `api-defs/get.sh --repin` | the version, the image that serves the document, and the sha256 of its content |
| `dockhand-openapi-1.0.51.json` (fetched, not committed) | what a `fnsys/dockhand:v1.0.51` server serves at `/openapi.json` | Dockhand API 1.0.51 - 272 paths, 395 operations |
| `dockhand-1.0.51/` | imported from the document by `make generate` | 395 operations, 687 models |

The document is Dockhand's, not this repository's: Dockhand is published by Finsys under the Business Source License 1.1, and that licence, not this repository's, covers the document. That is why it is fetched and not committed: what is in this repository is the pin, the definitions made from the document and the client generated from those. A document that is not the one pinned is refused, so a server that serves something else under the same version is noticed before anything is generated from it.

```bash
make spec              # fetch the pinned document unless it is already on disk; the targets below that read it do this first
make generate          # import + generate
make spec-refresh      # start the newest Dockhand, pin the document it serves, regenerate, and print what changed
make pandorest-diff    # what the document changes against its checked-in definitions, breaking changes marked
make apicheck          # the definitions match the document, and every operation has a method
make gencheck          # regenerate, fail if anything is uncommitted
```

Dockhand releases about once a week, and its API moves with it. `make spec-refresh` does the whole refresh: review the diff it prints, run the tests, commit. A workaround whose bug the new document fixes fails the import and names itself; delete it. The generated package records the version it was built from in its `APIVersion` constant.

The document is a description of intent, not of behaviour: the live suites (`acceptance/dockhand/`, `acceptance/tools/`) are what prove the shapes against a real server, and what they found is recorded below.

## How the document is made, and what that means

Dockhand writes the document from its route handlers by reading their source: the path, the method and the tag from where the handler sits, the parameters from what it reads off the address, the status codes from what it returns, and the body's fields from what it takes apart. That half is exact, and a new route is in the document the day it is written.

What a call answers is taken from an example where the handler's author wrote one. So:

- **A quarter of the calls say nothing of their answer.** 103 of the 395 declare a success and no content. For anything but a GET that is harmless: the client reads no model. The 53 GETs among them are each given one by the workaround `dockhand-undeclared-responses`.
- **An answer that is declared can be a part of the truth.** The container list declares five fields and a 1.0.51 server sends fifteen. A model made from the document then drops the rest without a word, which is why the suites hold every answer a tool reads to what the server sent.
- **No shape is shared.** The document has no component schemas, so every request and answer is a model of its own, named for its operation.

## Where the document is wrong

Shape bugs, fixed in the generated client by the importer's workarounds (`sdk/pandorest/workarounds`, listed in `dockhand-<version>/Service.json`). Each checks its bug is still in the document and fails the import once it is not.

- **`dockhand-audit-outside-api`: two calls sit outside `/api` beside their namesakes inside it.** `GET /audit` and `GET /audit/users` list the audit log and its users as `GET /api/audit` and `GET /api/audit/users` do, with their filters spelled another way (`entity_type` for `entityType`). Methods are named from a path with `/api` taken off, so each pair would make one name; the two outside are `GetAuditOutsideApi` and `GetAuditUsersOutsideApi`.
- **`dockhand-undeclared-responses`: 26 GETs declare a 200 and nothing of what it holds**; more do and have fixes of their own below, which give each its shape: the stack list, a stack's compose file and where each stack is kept, the git stacks, the backups, a host's container statistics and sizes, a container's files, the general settings, the licence, the tags and the icons of an environment's containers, the tags of its stacks, the list of selfh.st's icons, and the two calls a browser signs in through. Each answers one of three things, found by asking a 1.0.51 server:
  - JSON, which the client hands back as it came until a shape is declared for it: a container (Docker's own inspect document) and its inspect, the theme and a user's own preferences.
  - A stream of events (`text/event-stream`) that goes on until the caller hangs up: a container's log stream, the merged logs of several, the statistics streams, an environment's Docker events, the activity feed and the schedules.
  - A file: a tar archive for a container's files, an image and a volume; a picture for an icon; an export in the format asked for.
  - Could not be asked on a free server with nothing configured, and declared from their names and their neighbours: the audit log's events and export (an Enterprise licence), the single-sign-on calls, and a deploy run's log. The read sweep classifies each of these.
- **`dockhand-container-list`: a container in the list is declared with five fields.** Its id, name, image, state and status; a 1.0.51 server sends the command, when it was made, its health, how often it has restarted, its image's id, its labels, mounts, networks and published ports as well, and `systemContainer`, which is `dockhand` or `hawser` for a container that is Dockhand itself or one of its agents, told by its image's name. A port is Docker's own record, capitals and all (`PrivatePort`, `PublicPort`).
- **`dockhand-stack-list`: the stack list declares nothing.** It answers a list of stacks, each with its name, its state, the icon it was given, its containers' ids and, for each container, the service it is, its state, health, image, ports, networks and restarts. A port there is spelled another way than in the container list (`privatePort`, `publicPort`, and `display` as a person writes it).
- **`dockhand-stack-action-answers`: acting on a stack answers how it went, which no call declares.** Starting, stopping and taking down a stack declare a job's id; restarting and deploying declare nothing and describe a stream of events. Asked for JSON alone, as the client asks for everything, a 1.0.51 server does the work first and answers `success` with `output` or `error`.
- **`dockhand-vulnerability-count-options`: three lists are declared in the wrong place.** `GET /api/vulnerabilities/count` declares the images, containers and stacks its findings can be narrowed to beside its total; a 1.0.51 server sends them under `options`.
- **`dockhand-oidc-redirects`: the two calls a browser signs in through declare a 200 they do not give.** `GET /api/auth/oidc/{id}/initiate` and `GET /api/auth/oidc/callback` exist to send a browser on, to the identity provider and back from it; where they send it is their answer, handed back unfollowed.
- **`dockhand-scan-export-env`: exporting an image's scan needs an environment it does not declare.** `GET /api/images/scan/export` declares no `env`; a 1.0.51 server with its login on answers 400 `env is required` without one.
- **`dockhand-environment-record`: an environment is declared in parts.** The four calls that answer one declare between three and eleven of its fields, each differently, and a 1.0.51 server sends the same record from all of them, twenty-five fields from the list. `labels` is declared a string and is a list of them, sent and answered. And a connection test that fails says why in `error`, which neither test call declares.
- **`dockhand-wrong-answer-types`: three answers are declared as another type than is sent**, which the client could not read at all: a release's `changes` in the changelog are objects, a type and a text, not strings; the database health's `tables` is an object, how many are expected, found and missing, not a number; and a host's `uptime` is a fraction of seconds, not a whole number.
- **`dockhand-dashboard-stats-env`: the dashboard's statistics answer two shapes.** `GET /api/dashboard/stats` declares a list, one entry an environment, and with `env` given answers that environment's entry alone, an object. The client asks for the list and never sends `env`.
- **`dockhand-environment-create-fields`: creating an environment takes more than it declares.** `POST /api/environments` declares nine fields and takes every one the update does. A 1.0.51 server kept `hawserToken`, `tlsSkipVerify`, `tlsCa`, `collectActivity`, `collectMetrics` and `highlightChanges` on create; without the token an environment behind a Hawser agent cannot be made through the API at all.
- **`dockhand-image-answers`: the images of a host are declared as Docker spells them, and are not sent that way.** `GET /api/images` declares four fields an image (`Id`, `RepoTags`, `Size`, `Created`) and a 1.0.51 server sends nine spelled its own way: `id`, `repoTags` and the same again as `tags`, `repoDigests`, `size`, `virtualSize`, `created`, `labels` and `containers`, how many were made from it. The four declared decode all the same, since Go reads a field's name whatever its capitals, which is why the read sweep never caught it; the five undeclared were dropped. An image's history leaves out the `Tags` each layer carries, and pulling an image declares no answer at all.
- **`dockhand-volume-answers`: the volumes of a host likewise.** `GET /api/volumes` declares five fields in Docker's spelling and the server sends seven in its own: `name`, `driver`, `mountpoint`, `scope`, `created`, `labels` and `usedBy`, the containers that mount it. Reading one volume declares its labels and options as objects of nothing, where they are texts by name, and an entry of a volume's files leaves out `readonly`.
- **`dockhand-network-answers`: and its networks.** `GET /api/networks` declares six fields in Docker's spelling and the server sends seven in its own, with the address ranges under `ipam` and the containers on the network by their id. Reading one network is Docker's own record and is spelled as Docker spells it, but six of its fields are declared, two of them as objects of nothing.
- **`dockhand-prune-answers`: pruning declares no answer.** The five calls answer `success` with Docker's report of what went under `result`, and for all four kinds at once one report under each of `containers`, `images`, `volumes` and `networks`.
- **`dockhand-job-accept`: seventeen calls answer two ways, and nothing declared chooses between them.** Pulling an image, pushing one, pruning images, scanning one image or every image of an environment, making a stack, saving a stack's compose file, starting, stopping, restarting, deploying and taking down a stack, running a backup, restoring one, and looking after or verifying a backup's destination wait and answer how it went for a caller whose `Accept` asks for JSON alone, and answer `{jobId}` at once for any other. The fix gives each an `Accept` option, so that one method serves both: left out, the call waits. The last is deploying a git stack with its progress, `POST /api/git/stacks/{id}/deploy-stream`, which is of use only as a job: made to wait it answers `{"success":false,"error":"No result"}` and no more.
- **`dockhand-container-answers`: four calls about containers declare no answer.** `GET /api/containers/stats` answers a list with each running container's id and name beside its processor share, memory, network and disk counts; `GET /api/containers/sizes` a record by container id of what each has written and what its filesystem takes; `GET /api/containers/{id}/files` the path with its entries, each with its kind, size, permissions, owner, group and when it changed; and `POST /api/containers/check-updates` how many containers were checked and have a newer image, with each one's finding: whether the registry has another image under the name, why it could not be asked, whether the container is Dockhand's own or labelled to be left alone, and a newer version tag when Dockhand is set to look for one.
- **`dockhand-update-answers`: what is noted of newer images, and a container's update schedule, are declared in part.** A pending update declares its `newerVersion` an object with nothing in it, and it holds the tag, how far a step it is (`bump`), the tags passed over and the image's digest. `GET /api/auto-update` declares an object with nothing in it and answers a record by container name of each one's schedule. Reading or saving one container's schedule answers the stored record, with its number, environment, the container's name and when it was made, changed, last checked and last updated, where only the schedule is declared; and none of it is always there, since a schedule switched off answers `{"success":true,"deleted":true}` in the record's place.
- **`dockhand-container-update-fields`: making a container again takes more than it declares.** `POST /api/containers/{id}/update` declares an image, a name and two flags, and says in words that its body carries what a container is made with. It takes every field `POST /api/containers` does.
- **`dockhand-activity-answers`: what a container did is declared with half of what is kept.** An event in `GET /api/activity` declares its id, the environment's number, the container's name, the action and the time, and is sent with the environment's name, the container's id, its image and `actorAttributes` as well, which is what Docker said of it: the exit code of a death, the signal of a kill, the old name of a rename, and the container's labels. `GET /api/activity/stats` declares `byAction` an object with nothing in it, and it is a record by action of how many there are.
- **`dockhand-disk-answers`: what a host's disk holds is declared an object with nothing in it.** `GET /api/system/disk` answers Docker's own account under `diskUsage`, in Docker's spelling: `LayersSize`, and each image, container, volume and piece of build cache with its size and whether anything uses it. The fix declares what the tools read of it; a server sends more.
- **`dockhand-schedule-answers`: a schedule and a run of one are declared in part, and a run's log under the wrong name.** `GET /api/schedules` declares nine fields of a schedule and a server sends what it does in words, its environment's name, its latest run and its latest few as well. A run is declared with four fields in `GET /api/schedules/executions` and is sent with which schedule it was of, what set it off, how long it took, what it did (`details`, by its kind) and why it failed. `GET /api/schedules/executions/{id}` declares the run's `log`, and the server sends `logs`.
- **`dockhand-registry-answers`: a registry is declared without the name it signs in with, and a push with a job for its only answer.** A registry is sent with `username`, `createdAt` and `updatedAt` wherever one is sent, beside the five fields declared. `POST /api/images/push` declares `jobId`, and to a caller that asks for JSON alone it answers `status`, `message` and `targetTag`, or `status` `error` with why.
- **`dockhand-notification-answers`: a channel is declared with part of how it sends, an event without what it is, and a tie to an environment without either end.** A channel's `config` is declared with six fields where a channel is read and with none where one is made or changed, and a server sends nine: the addresses, or the mail server, its port, whether it speaks TLS from the first word, the user name, a mask for the password, the sender's address and name and the recipients, with `createdAt` and `updatedAt` beside them. An event in `GET /api/notifications/trigger-test` declares its id and label and is sent with a `description`, a `group` and a `scope`. A channel's tie to an environment is sent with the environment's number, the channel's name and kind, whether the channel is itself switched on, and when the tie was made and changed.
- **`dockhand-scan-answers`: the calls about vulnerability scans declare neither what they are asked with nor what they answer.** `GET /api/vulnerabilities`, its count and its export declare no parameter at all: a server finds nothing without `env`, and narrows by `q`, `severity`, `image`, `container` and `stack`, orders by `sort` and `dir`, and pages by `limit` and `offset`. A finding is declared an object with nothing in it, and the list without the `summary` it is sent with. `GET /api/images/scan` declares its `result` the same way. `GET /api/settings/scanner` declares no answer, and saving the settings answers them without the images the scanners are run from. `POST /api/images/scan` and `POST /api/vulnerabilities/scan-all` declare a stream of events for their only answer, and are two more of the calls that answer how the work went to a caller that asks for JSON alone and a `jobId` to any other.
- **`dockhand-user-answers`: the calls about users and the login leave out fields the server sends.** `GET /api/users` declares eight fields of a user and is answered with `mfaEnabled`, `lastLogin` and `createdAt` as well. `POST /api/users` declares four fields of the user it made and is answered with `displayName`, `isActive`, `createdAt` and `autoLoggedIn` too. `GET` and `PUT /api/auth/settings` declare `authEnabled` and `defaultProvider` and are answered with `sessionTimeout` beside them, which the request can set and nothing declared could read back.
- **`dockhand-sso-answers`: an OIDC provider is declared by the five fields that name it.** The four calls that answer one declare `id`, `name`, `enabled`, `issuerUrl` and `clientId`. The server sends the rest of what was saved as well: `redirectUri`, `scopes`, the claims it names for a user's name, email and display name, `adminClaim` and `adminValue`, `roleMappingsClaim`, when it was made and changed, and a mask where its `clientSecret` would be.
- **`dockhand-settings-answers`: the general settings and the licence declare no answer, and one setting the wrong type.** `GET` and `POST /api/settings/general` both answer every general setting, by the names the request to save them declares, so the request's fields are given to both answers. That request declares `externalStackPaths` a text; the server passes a text over without a word and takes, and answers, a list of paths. `GET /api/license` on a server with no licence answers `active`, `valid` and `hostname`.
- **`dockhand-template-answers`: a template is declared by what names it, and a source of templates without whether it is Dockhand's own.** `GET /api/templates` declares a template's id, type, title, description, logo, categories, source, image and two links; the server sends what it would be run with as well: `repository` with its `stackfile` for a stack, and for a container `ports`, `volumes`, `env`, `restartPolicy` and `network`, with a `note`. `POST /api/templates/compose` declares the template it is given by five of its fields and writes the rest into the compose file when it is sent them, so they are declared there too. `GET` and `POST /api/templates/sources` are answered with `sourceId`, `builtin` and `sortOrder` beside the four fields declared.
- **`dockhand-tag-answers`: a tag is declared without its icon, and what is tagged is not declared at all.** `GET /api/tags` declares a tag by its number, name and colour, and the server sends its `icon` as well, which the calls that make and change one take. `GET /api/container-tags` and `GET /api/stack-tags` declare no answer, and each answers the numbers of the tags every container, or every stack, of the environment has, by the container's or the stack's name.
- **`dockhand-label-answers`: the colours of the labels of environments are declared as an object of nothing.** `GET /api/labels` answers the colour of each label that has one, as `#rrggbb`, by the label's name.
- **`dockhand-icon-answers`: the calls about icons declare no answer, or an object of nothing.** `GET /api/container-icons` answers the icon each container of the environment was given, by the container's name. `GET /api/icons/selfhst-manifest` answers the list of selfh.st's icons, each with its `Name`, the `Reference` it is asked for by, whether it comes as `SVG`, `PNG` and `WebP` and for a `Light` and a `Dark` background, its `Category` and its `Tags`. `POST /api/icons/selfhst/batch` declares the icons it answers as an object with no fields, and they are pictures written as `data:` addresses, by reference.
- **`dockhand-preference-answers`: the calls about what the web interface remembers declare an object of nothing, half an answer, or none.** Reading, saving and forgetting the columns of a grid (`/api/preferences/grid`) declare the preferences they answer as an object with no fields, and each answers the columns saved for every grid, by the grid's id, each column with its `id` and whether it is `visible`. `GET` and `POST /api/preferences/favorites` declare a list of names and `GET` and `POST /api/preferences/favorite-groups` a list of groups, and each answers the one list a server keeps for the environment, names and groups together in order. `PUT /api/settings/navigation` declares no answer, and answers `success` with the pages as they now are for the scope that was changed.
- **`dockhand-secret-provider-answers`: a secret provider is declared without its dates, and a stack's provider as an object of nothing.** `GET` and `POST /api/secret-providers` and `GET` and `PUT /api/secret-providers/{id}` declare a provider by its number, name and type, and the server sends `createdAt` and `updatedAt` as well. `GET /api/stacks/{name}/env` declares the stack's `secretProvider` as an object with no fields, and it answers the provider's `type` and `name`, or null for a stack that has none.
- **`dockhand-git-answers`: the git calls declare a handful of fields, or no answer at all.** A repository is declared with five fields and a 1.0.51 server sends thirteen more: when it was saved and changed, how its own copy stands, and what is left of the days a repository was itself what was deployed (`composePath`, `environmentId`, `autoUpdate`, `webhookEnabled` and the like, which nothing in the API sets any more); in the list, the name and kind of its credential as well. Trying a repository or a git stack also answers the `branch` and its newest commit as `lastCommit`. `POST /api/git/branches` declares each branch as an object of nothing and answers its `name` and `sha`. `POST /api/git/preview-env` and `POST /api/git/stacks/{id}/env-files` declare `vars` as an object of nothing, which is each variable's value by its name. The five calls that list, make, read, change and remove a git stack declare no answer, and all but the last answer the same record. Making and changing one declare six and four fields of a body the server reads twenty-two and seventeen of: the compose file's path, the extra `.env` file, the branch, the schedule, the four switches of a deploy, the variables. Fetching one answers what changed, and deploying one what compose printed. One field is left undeclared on purpose: `POST /api/git/stacks/{id}/deploy` answers `resolvedSecrets`, the values of the stack's secrets, and the client is not to hold them.
- **`dockhand-backup-answers`: of the 31 backup calls only the instance's declares what it answers.** The others answer a destination, a configuration, a snapshot, what is in one, how a run or a restore went, or a plain success, and each is declared as a 1.0.51 server started with `FEAT_BACKUPS_ENABLED=true` sends it. Two request fields are put right as well: `POST /api/backup/restore/preview` declares `volumeDestinations` as an object, and the server takes a list of `{volume, target}` and answers a 200 holding `.map is not a function` to an object; `POST /api/backup/restore` declares its entries as objects of nothing, and the server wants `{volume, kind, target}` with `kind` `volume` or `path`.
- **`dockhand-stack-answers`: the calls about one stack declare no answer, or the wrong one.** Reading a stack's compose file answers its text with where the file and its `.env` are kept; `GET /api/stacks/sources` answers a record by stack name of how each is kept; making a stack answers `success`, whether it was `started` and what compose printed, or a `jobId`; saving the compose file answers `success`, or a `jobId`; and saving the variables answers `success` and how many were sent. A deploy's `details` are declared as an object of nothing and hold the options it ran with, what it made and started, its exit code, a digest of the file it ran and the name of its log. And `POST /api/stacks/scan` declares what it found as a name and what it skipped as text, where both are records of the name, the compose file, the `.env` beside it and how many services it has: as text, a scan that skipped anything could not be read at all.

One setting of the generator is on for this document: a property a request body lists as required is always sent, an empty string as `""` and not left out. Saving a stack's `.env` file with nothing in it is how the file is removed, and a body with no `content` at all is refused.

Left as the document has them:

- Three request bodies declare one field under two spellings, `cronExpression` and `cron_expression`, `vulnerabilityCriteria` and `vulnerability_criteria` (setting a container's auto-update), `eventTypes` and `event_types` (a notification channel). The client keeps the first.

## What the document never declares: dates, fixed sets and ids

The document declares every date a plain string, every value from a fixed set a plain string, and every id a plain number. Each is declared here instead (`sdk/pandorest/workarounds/value_sets.go` and `ids.go`), read off a recording of every answer a real 1.0.51 server gave both live suites, and the live sweep holds them to the server from then on: it fails an answer with a date no form reads or a value no set lists.

- **Dates come in three forms.** `2026-10-10T13:08:26.073Z` with any number of fractional digits, `2026-10-10 13:08:26` with a space and no zone (Dockhand's own database's, which is UTC), and `2024-08-16 00:27:23+00:00`. 21 names are dates wherever they sit (`createdAt`, `updatedAt`, `lastSync`, `scannedAt`, `lastLogin`, `hawserLastSeen`, `lastUsed`, `lastChecked` and the rest). The one number that is a date is `timestamp` in `GET /api/containers/{id}/stats`, in milliseconds.
- **Left as text: when a file inside a container or a volume was changed** (`modified`), written `2026-10-10T09:39:00` with no zone, in whatever zone the container keeps.
- **24 sets of values**, among them how an environment is reached (`socket`, `direct`, `hawser-standard`, `hawser-edge`), a container's state and health, a job's status (`running`, `done`, `error`), a stack's (`running`, `partial`, `stopped`, `created`), a scheduled run's and a deploy's, a finding's severity and a compose check's, the kinds of notification, secret provider, schedule, sign-in and template.
- **One name is several things.** `status` is a job's own beside the free text of its progress lines, and a stack's own beside each container's (`Up 6 seconds`); `type` is eight different things; `protocol` is `http` or `https` on an environment, `tcp` or `udp` on a port and a whole address on `GET /api/hawser/connect`; `severity` is also a search parameter that takes several with commas between. Each set says where it holds.
- **Left as text because Dockhand keeps whatever it is sent:** a config set's restart policy, mount mode and port protocol (it saved `whenever`, `zz` and `icmp`).
- **Left as text because the words are Docker's**, open to plugins and versions: a network's and a volume's driver and scope, a mount's type and mode, a container's status text, and what a container did in the activity log.
- **14 kinds of id** are told apart, all Dockhand's own records: environment, notification, registry, user, role, git repository, git credential, git stack, secret provider, config set, tag, template source, backup destination and backup configuration. `env` is the environment's id as a query parameter on nearly every call, and a container's list of variables in four bodies.
- **Left as plain ids:** Docker's (a container, an image or a network is named by its id, the start of it or its name in the same place), a job's and a deploy run's (used once), a schedule's and an audit record's (whose id it is depends on the type beside it), and a snapshot's, which is restic's: the id restic gave it, or the start of it.

## What the server does

Found by running a 1.0.51 server with a Hawser 0.2.50 agent.

### Who is asking

- **A fresh server has no login and no users.** Every call is answered with nothing sent, and `GET /api/auth/session` says `{"authenticated":false,"authEnabled":false}`.
- **The first user is made without a login, and is an administrator.** `POST /api/users` answers 201 while there is no user. Login is then switched on with `PUT /api/auth/settings` and `{"authEnabled":true}`.
- **With login on, a call sent nothing and a call sent a wrong token are answered alike**: 401, `{"error":"Unauthorized","message":"Authentication required"}`.
- **`/api/health` and `/openapi.json` stay open** with login on.
- **A token is made by a session, not by a token.** `POST /api/auth/login` sets a cookie, `dockhand_session`, and `POST /api/auth/tokens` wants that cookie and the password again. It answers 201 with the token, `dh_` and 43 characters, once: no later call gives it back, only its first eight characters as `tokenPrefix`.
- **A token is not a session, and some calls answer a session alone.** `GET /api/profile` and `GET /api/profile/preferences` answer 401 `Not authenticated` to a token the server takes everywhere else, and answer a session's cookie. A token it does not take at all is told `Authentication required` instead, which is how the two are told apart.
- **A token is read under `/api` and nowhere else.** The two audit calls outside it, `GET /audit` and `GET /audit/users`, answer a token with a redirect to the login page once the login is on.
- **The roles are listed while the login is off, and are the Enterprise edition's once it is on.** `GET /api/roles` answers the built-in roles on a server with no login, and 403 `Enterprise license required` on the same server with its login on.
- **`GET /api/auth/session` does not know a token.** Asked with a valid bearer token it says `authenticated: false`: it reports on the cookie alone.
- **A user holds at most 25 API tokens.** The next one asked for is refused, 400 `Maximum of 25 API tokens per user`, until one is revoked: a suite that mints a token each run and never revokes it shuts itself out of a server it is run against often enough.
- **Trying a single sign-on provider and switching a user's second factor off are a session's as well.** `POST /api/auth/oidc/{id}/test` answers a token 403 `Admin access required`, and `DELETE` and `POST /api/users/{id}/mfa` answer it 403 `Permission denied`, whoever the token belongs to; each answers a browser that signed in.

### Environments

- **An environment is reached one of four ways**, its `connectionType`: `socket` (a path on the server's own disk), `direct` (a host and port), `hawser-standard` (an agent that listens, with a token) and `hawser-edge` (an agent that calls in).
- **A connection can be tried before it is saved.** `POST /api/environments/test` answers 200 either way, with `success` and, when it failed, why: a wrong agent token is `Invalid token - check that the Hawser token matches`. An agent's answer carries its name, version and what it can do.
- **Making an environment answers its labels as text.** `POST /api/environments` answers the record with `labels` a string holding the JSON of the list, `"[\"a\",\"b\"]"`, or null when none were given; reading the environment, listing it and updating it all answer the list itself.
- **Updating an environment keeps what it is not sent**, and an empty text is nothing sent as far as the generated client goes, so one thing cannot be cleared by it: `publicIp` is only forgotten when it is sent empty, which `ForgetEnvironmentPublicIP`, written by hand in `sdk/dockhand/service.go`, does. A name another environment has answers 409, in words about the folder Dockhand keeps the environment's stacks in, which it renames with the environment.
- **What Dockhand does for an environment by itself is five settings, each its own call**: `timezone`, `update-check`, `image-prune`, `disk-warning` and `remote-stacks-dir`. A timezone there is none of answers 400. Everything else is saved whatever it says: a cron expression nothing can read (the schedule is then kept and never runs), any prune mode beside `dangling` and `all`, any disk warning mode beside `percentage` and `absolute`. The remote stacks folder is forgotten by a save that names none. `PUT /api/environments/{id}/image-prune` runs the prune now, outside its schedule.
- **`GET /api/host` says less of a host reached with no agent.** Its `uptime` and `freeMemory` are 0 for a `direct` connection; a socket and an agent give both.
- **A saved environment does not remember an agent Dockhand calls.** `hawserVersion`, `hawserAgentName` and `hawserLastSeen` stay null on a `hawser-standard` environment whose agent answers; what the agent is comes from testing the environment. One whose agent calls in (`hawser-edge`) has all three from the moment it does.
- **An environment an agent calls in for is saved with a name and nothing else**, and is not reached until an agent calls `/api/hawser/connect` with a token made for it. Until then trying it answers `Edge agent is not connected`, and its containers are an empty list rather than an error. `GET /api/hawser/connect` lists the agents connected now, each by its environment's number.
- **A token is answered once and listed by how it begins.** `POST /api/hawser/tokens` takes a name and the environment's number, and answers the token; `rawToken` gives one of the caller's own choosing, of any length, three characters included; `expiresAt` is saved whatever it says. A missing name or number answers 400, an environment there is none of 500, and a token is made for an environment of any kind, where it is of no use.
- **An environment has one token that works.** Making another ends the one before it and closes the call of the agent connected with it, at once. Revoking (`DELETE /api/hawser/tokens?id=`) does the same and leaves the environment with none; a number no token has is answered `success` all the same. A token that no longer works stays on the list, `isActive` false, until its environment is removed.
- **One refused token shuts an address out for five minutes.** An agent that calls with a token Dockhand does not take is turned away, and every call from the same address is then turned away unlooked at, the right token's among them, until five minutes after the refusal (still refused at 263 seconds, let in at 302). An agent whose token was replaced or revoked calls again with it a second later, so this follows every replacing of a token under a running agent. The agent sees `failed to receive welcome` and Dockhand logs `Rate limited`.
- **`GET /api/system/disk` is Docker's own account of its disk**, measured when asked, and the one place a volume's size is told. It answers `{"diskUsage": null}`, not an error, for an environment there is none of or a host that does not answer in time, and 400 with no `env`.
- **Dockhand shows its own filesystem, less what it keeps to itself.** `GET /api/system/files` lists a directory (the root unless `path` says otherwise) and leaves `/etc`, `/proc`, `/root` and its own database and key out of what it lists; asked for one of them, or for a path that reaches one by `..`, it answers 403 `Access denied`. A file answers 400, a path that is not there 404. `/content` reads a text file up to 10 MB, and answers 400 for a directory and for a larger file, in different words. `POST` makes a directory and the ones above it, and answers 409 when it is there already. There is no call that removes one.
- **`GET /api/environments/detect-socket` looks in the usual places on Dockhand's own machine** and answers each socket it knows of with whether it is there, beside the home directory of the user Dockhand runs as.
- **Nearly every call about a Docker host takes it as `env`, the environment's number.** With no `env`, or one that is not a number, the container list answers 200 with an empty list rather than an error. With a number no environment has it answers 404, `{"error":"Environment not found"}`.

### Containers

- **A container is found by its id, the start of its id, or its name.**
- **`GET /api/containers/{id}` is Docker's own inspect document**, with Docker's capitals (`Id`, `State`, `Config`); `/inspect` is the same with `divergence` added.
- **The list holds every container, running or not**, unless `all=false` is sent, which leaves it the running ones.
- **Logs are one text**, `{"logs": "..."}`, each line led by its time. The merged logs of several containers are only to be had as a stream.
- **Start, stop and restart answer `{"success":true}` once done**, and stopping a stopped container is no error. One that is not there answers 500, `{"error":"Failed to restart container"}`, and so does one asked for with no `env`.
- **Pausing what is paused, and unpausing what is not, answer 500.** Renaming to a name that is taken answers 500 too. Removing a running container answers 500 unless `force` is sent, and removing one that is not there answers `{"success":true}`, so that a container is gone is read from the list.
- **Running a command names the host `envId`**, where every other call names it `env`. It answers `stdout`, `stderr` and `exitCode` once the command ends; a command the container has not is an answer, with exit code 127 and Docker's words in `stdout`.
- **Making a container does not start it unless `startAfterCreate` is sent.** It pulls the image when the host has not got it, and says so (`imagePulled`). A container that is made and then cannot be started, because a port is taken or its network is not there, answers 500 `Failed to create container` and is left on the host as it was made. One made with no `name` is named `undefined`. `ports` is a record by the container's port, `{"80/tcp":{"HostPort":"8080","HostIp":"127.0.0.1"}}`, one host port to a container port; a host port given as a bare string answers 500.
- **Making a container again (`/update`) keeps what it is not given and replaces what it is.** Sent an image alone, the new container has the old one's variables, labels, ports, mounts, networks, restart policy and limits. Sent `env`, `labels`, `ports` or `volumeBinds`, the new container has exactly those and none of the old: an empty list or record is none at all. It is not started unless `startAfterUpdate` is sent. An image the host has not got answers 404 `No such image` unless `repullImage` is sent, after the old container was stopped, and the old one is started again. `repullImage` with no `image` answers 500, `Cannot read properties of undefined`.
- **It makes Dockhand's own container again as readily as any other**, and so the tools refuse one the list marks `systemContainer`.
- **A batch update pulls each container's image and makes each again, whether or not anything newer came**, one after another in one call, each taking as long as its container takes to stop. What Dockhand had noted for a container is kept under the old container's id and is not cleared.
- **Limits (`/update-runtime`) are Docker's own fields, capitals and all** (`Memory`, `NanoCpus`, `RestartPolicy.Name`), and are taken by a container that is stopped too. A limit of 0 changes nothing, so one cannot be taken off this way. A body with none of the fields it knows answers 400 with the list of them.
- **A check for newer images notes two things.** That the registry has another image under the very name and tag (`hasUpdate`, and `hasImageUpdate` once noted); and, only when `/api/settings/semver` is switched on, a newer version tag (`newerVersion`), for which a note is kept even when the image under the tag in use has not changed. A container labelled `dockhand.update=false` is not looked at (`updateDisabled`). An image built on the host, or one whose registry wants credentials Dockhand has not got, is an `error` beside the finding and no failure of the call.
- **Release notes come from GitHub and nowhere else.** `GET /api/containers/{id}/version-notes` takes the version tags as a comma-separated `versions`, and for an image that does not say where its source is answers no notes, `source` null and no error.
- **A schedule is kept by the container's name, and anything is saved.** `GET /api/auto-update/{name}` answers a schedule switched off, daily at three, for a container that has none and for a name no container has. Saved with a cron expression nothing can read, or none, the schedule is kept as `custom` and never runs; `vulnerabilityCriteria` takes any text, and the five that mean something are `never`, `any`, `critical_high`, `critical` and `more_than_current`. Saving with `enabled` false deletes it.
- **Files inside a container are reached two ways, and only one works on a stopped container.** Listing, reading, making, moving, changing permissions and removing run a command in the container (`ls`, `cat`, `mkdir`, `mv`, `chmod`, `chown`, `rm`) and answer 500 with the command's own words when it fails, and `container is not running` when it is not. Writing a file's content, sending files in and fetching an archive out go through Docker's copy, and work on a container that is stopped.
- **Writing a file's content to a path that is a directory replaces the directory with the file**, and everything that was in it is gone; the call answers `{"success":true}`. Written over a file, or over a link, the file is root's and mode 644 afterwards, whatever it was. A path whose directory is not there answers 500.
- **Moving (`/files/rename`) is `mv`**: onto a file that is there it replaces it without a word, and onto a directory it moves the thing inside. Removing is `rm -rf`, a directory with everything in it; `/` and a few system paths such as `/etc` answer 400 `Cannot delete critical system path`, and `/tmp` or an application's own directory at the root do not.
- **Making a directory makes the ones above it**, and making what is there already answers `{"success":true}`, unless a file is in the way, which answers 409.
- **Files are sent in as a form**, each a part named `files`, with an optional `owner`; they replace files of the same names. A directory that is not there fails the lot with 500 and the reason for each under `details`.
- **A plain archive fetched from a host behind a Hawser agent is cut short.** `GET /api/containers/{id}/files/download` answers a tar, and from a host Dockhand reaches itself it is whole. From behind an agent the answer's length is the length the agent sent it compressed, so the tar stops part way through its first header. Asked for with `format=tar.gz` it is whole from either, which is how the tools ask for every archive. A path that is not there answers 500, where the document says 404.
- **What containers did is kept by Dockhand, not asked of Docker.** It keeps Docker's own events for each environment it is set to collect activity from, from when it began watching it, and so it knows of containers that have since been removed. An event is kept a moment after it happens, not as it happens.
- **`GET /api/activity` is narrowed by five things**: `environmentId`, `containerName` (any part of the name), `actions` (Docker's words with commas between: `die,oom`), `fromDate` and `toDate`. The times are ISO 8601, and one that cannot be read matches nothing and is no error. It gives the latest first, `limit` at a time from `offset`, and `total` counts all that matched. The exit code, the signal and the old name are text under `actorAttributes`, as `exitCode`, `signal` and `oldName`.
- **The two calls beside it name the host differently.** `GET /api/activity/stats` and `GET /api/activity/containers` take `environment_id`, where the list takes `environmentId` and nearly everything else `env`.
- **Clearing it clears every environment's.** `DELETE /api/activity` takes nothing to narrow it: not one environment, not one container, not a time.
- **Many things are done at once through one call, which says how many succeeded and not which.** `POST /api/batch` takes an `entityType`, an `operation` and `items`, each an `id` and a `name`: `start`, `stop`, `restart`, `pause`, `unpause` and `remove` for `containers`, `start`, `stop`, `restart`, `down` and `remove` for `stacks`, and `remove` alone for `images`, `volumes` and `networks`. Asked for JSON it answers `{"type":"complete","summary":{total, success, failed}}`; asked as a job, the job's lines say how each item went. Removing a container there is none of is counted a success.

### Registries

- **A registry is tried before or after it is saved**, by `POST /api/registries/test` with an address and a login, or with `registryId`. It answers 200 whatever it finds: `connectivity`, `authenticated` (null when no login was tried, as for a registry that asks for one and is given none, which is still `success`) and a message. An address with no scheme is tried as one that speaks TLS, and fails to connect when it does not.
- **A change must carry the address.** `PUT /api/registries/{id}` with a name alone, or `isDefault` alone, answers 500 `Failed to update registry`; with the address beside it, it is saved. What is not sent is kept, the user name and password among it, and both sent empty are forgotten, which the generated call cannot ask for: `ForgetRegistryCredentials`, written by hand in `sdk/dockhand/service.go`, does. A name another registry has answers 400. Making a registry answers 201.
- **Any registry is removed when asked**, the default one and the record of Docker Hub a fresh server comes with included, and there is then no default until another is made it (`POST /api/registries/{id}/default`, or `isDefault` in a change).
- **A host is signed in to a kept registry by its address.** Pulling an image whose name leads with a kept registry's address, and pushing to one, use the login kept for it; with none kept, the host's Docker is turned away, `no basic auth credentials`.
- **A push names the image three ways and only one does what it says.** `newTag` is the whole name pushed under, repository and tag (`org/app:1.2`; with no tag, `latest`), not a tag. `imageName` is used when `newTag` is left out, less the registry it leads with, and with neither the image's first name is. `imageId` takes a name as well as an id. Dockhand gives the host's image the registry's name to push it and leaves that name on the host, also when the push then fails. An image there is none of answers 500, a registry there is none of 404, and a registry that refuses the push 500 with `status` `error`.
- **What a registry holds is listed, searched and read by tag.** `GET /api/registry/catalog` lists a registry's images a page at a time and answers 400 for Docker Hub, which has no list; `/search` with a `registry` looks through that list for a part of a name, and with none searches Docker Hub; `/tags` gives Docker Hub's tags in full, a page at a time and the newest first, and a registry's own as names alone, all at once, the size of each being `/tag-info`. An image the registry has none of answers 500 `Image not found in registry`.
- **A registry's own refusal comes back as Dockhand's.** When the registry answers 401 to what Dockhand signs in with, the catalog, the tags and a delete answer 401 themselves, `Authentication failed. Check the registry credentials.`, which is the status Dockhand's own login answers with.
- **Deleting a tag deletes what it points at.** `DELETE /api/registry/image` finds the tag's contents and deletes those, so every other tag of that image with the very same contents goes too, and the image stays in the catalog with no tags. A second go answers 404, Docker Hub 400, and a registry not set to allow deleting 405.

### Schedules

- **A schedule is named by its type and a number, and the number means something else for each type.** For `container_update` it is the number of the container's update record, for `env_update_check` and `image_prune` the environment's, for `system_cleanup` one of five fixed jobs. The list gives both.
- **Not everything that can be run is listed.** An environment's check for newer images is listed only while it is switched on, though it can be run and turned over when it is not; an environment's image prune is listed once its settings have been saved, switched on or not.
- **Running one answers at once**, `Schedule triggered successfully`, and the run is kept when it ends: `GET /api/schedules/executions` gives the runs, the latest first, with `status` one of `queued`, `running`, `success`, `warning`, `failed` and `skipped`, and `details` by the kind of run. A list of runs leaves `logs` null; one run read by its number has them.
- **The runs are narrowed by** `scheduleType`, `scheduleId`, `environmentId`, `status` or a comma-separated `statuses`, `triggeredBy` (`cron`, `manual`, `webhook`), `fromDate` and `toDate`. A status there is none of matches nothing and is no error.
- **A stack brought up is kept as a run too**, of type `stack_deploy` with `scheduleId` 0, among the runs of schedules.
- **There is no call that switches a schedule one way.** `POST /api/schedules/{type}/{id}/toggle` turns it over and answers how it then stands. Dockhand's own jobs answer 400 `System schedules cannot be paused` there; three of them, numbered 1, 2 and 4 (clearing old runs, old container events and the scanners' cache), are turned over by `POST /api/schedules/system/{id}/toggle`, which answers 400 `Unknown system schedule` for the rest.
- **Removing a schedule means three things.** A container's update schedule is forgotten, record and all; an environment's image prune is forgotten and no longer listed; an environment's check for newer images is switched off and keeps how it was set. Removing one that is not there answers `success` all the same, and Dockhand's own jobs answer 400.
- **Whether the page that lists schedules hides Dockhand's own jobs** is `GET`/`PUT /api/schedules/settings`, a preference of the interface and nothing a schedule goes by.

### Notifications

- **A channel is mail or an address.** Its `type` is `smtp`, with a mail server, port, sender and recipients, or `apprise`, with `urls` that each begin with the service they are for: `json` and `jsons` for a webhook sent JSON, `ntfy`, `gotify`, `discord`, `slack`, `tgram`, `pushover`, `mmost`, `signal`, `workflows` and `apprise`. One that begins any other way is saved and fails when it is used, `Unsupported Apprise protocol`. An address on Dockhand's own machine is not sent to: `loopback address blocked`.
- **Two channels may have one name.** Nothing about a channel is unique but its number.
- **An address is given back whole, and a mail password never.** A channel's `urls` come back as they were saved, with the token or login each carries, to anyone who may read channels. A mail password comes back as `********`, and that mask sent in a change is taken to mean the password that is kept.
- **A change keeps what is not sent, and takes how the channel sends whole.** `PUT /api/notifications/{id}` with a name alone changes the name. A `config` replaces the one there is: mail with any of its server, port, sender or recipients missing answers 400, and so do `urls` with none in them.
- **Who hears of what is decided in two places.** An event that happens on an environment (`scope` `environment`, 34 of the 41) goes to the channels tied to that environment, by the list of events the tie holds, and the channel's own `eventTypes` are not looked at. An event of Dockhand's own (`scope` `system`: its license, and its backup repositories) goes to the channels whose own `eventTypes` name it. A channel's own list is saved whatever it says, names of no event among it; a tie's is cut down to the events of an environment as it is saved.
- **A tie is `POST /api/environments/{id}/notifications`** with the channel's number, and starts with every event of an environment whatever the channel's own list says. A second for the same channel answers 409, a channel there is none of 500 `FOREIGN KEY constraint failed`, an environment there is none of 404. Removing a tie answers `success` whether or not there was one. Removing a channel removes its ties.
- **Switched off, neither sends.** A channel that is off is sent nothing, tied or not; a tie that is off keeps its events and sends nothing. The tie says which with `enabled` and `channelEnabled`.
- **A test is an answer and not an error.** `POST /api/notifications/test` tries a channel that is not saved and `POST /api/notifications/{id}/test` one that is; both answer 200 with `success`, and `error` in the words of the service or mail server when it was turned away. Only nowhere to send at all is refused, with 400.
- **An event is set off by hand for an environment**, with `POST /api/notifications/trigger-test`, a `payload` of `title` and `message` and an `environmentId`. It answers how many channels took it under `sent`, and `success` false when any channel it went to did not, without saying which. Of Dockhand's own events only `license_expiring` is set off with no environment. The other six answer 400 without one, and with one are sent by that environment's ties, which hold no event of Dockhand's own: `sent` 0, always. They cannot be tried.
- **Dockhand looks for a newer version of itself through its own Docker socket, and answers "none" when it cannot look.** `GET /api/self-update/check` finds its own container through `/var/run/docker.sock` and answers `updateAvailable`, `currentImage`, `newImage`, `latestVersion`, `containerName` and `isComposeManaged`. Without that socket it answers 200 with `updateAvailable` false and an `error` (`Check failed: Error: connect ENOENT /var/run/docker.sock`), so the two are told apart only by `error`. It asks the internet each time. `POST /api/self-update` replaces Dockhand's own container, and has no tool.
- **What Dockhand says of itself as a product is the same for everyone.** `GET /api/legal/license` and `GET /api/legal/privacy` answer the whole text as `content`, some 24,000 and 14,000 characters; `GET /api/dependencies` lists the 280 pieces of software it is built from and runs, each with `name`, `version`, and mostly a `license` and a `repository`.

### Vulnerability scans

- **A scanner is a container on the host that has the image.** Dockhand runs `grype`, `trivy` or both, from `anchore/grype` and `aquasec/trivy` on Docker Hub unless told, and each keeps its database in a volume of its own on that host, `dockhand-grype-db` and `dockhand-trivy-db`. The first scan pulls the image and downloads the database.
- **What scans is an environment's own, and where it is run from is everyone's.** `POST /api/settings/scanner` with `envId` sets that environment's `scanner` (`none`, `grype`, `trivy`, `both`) and what each scanner is run with; with none it sets what every environment with no setting of its own goes by. `grypeImage` and `trivyImage` are one for all environments whichever is named. Only what is sent changes. An `envId` that is no environment's is saved all the same.
- **An environment that scans with nothing answers a scan as done.** `POST /api/images/scan` there answers 200, `stage` `complete`, `Scan complete - found 0 vulnerabilities` and no `results`; a `scanner` in the body that is neither `grype` nor `trivy` is answered the same way; and `POST /api/vulnerabilities/scan-all` answers that it scanned every image and none failed. Nothing ran. A fresh server is set to `none` everywhere.
- **A scan is answered two ways, like a pull.** Asked for JSON alone, the call waits and answers the last event of the scan: `stage`, `message`, and one entry in `results` for each scanner that ran, each with a `summary` by severity and its `vulnerabilities`. Asked otherwise, it answers a `jobId`, whose lines are the scanner's own progress and whose result is the same answer. A scan that fails is a 200 with `stage` `error` and the scanner's whole log in `message`; as a job it ends in `error` with `success` false. A `scanner` in the body overrides the environment's for that scan.
- **A scan is kept under the name it was asked with.** Asked for by an image's id, the scan is listed under that id. `GET /api/images/scan` gives the latest scan of an image, by whichever scanner ran last or by the one named, and takes a name or an id. Every scan is kept, and the reads give the latest by each scanner. No call removes one: a nightly job of Dockhand's own does, `Vulnerability scan retention`, which by its own account keeps the 10 newest scans of an image by each scanner and removes those of an image gone from the host for 7 days. Both numbers are general settings, `scanRetentionKeep` and `scanRetentionGraceDays`. The job was read about and not watched at work.
- **The findings are of the images a host still has.** `GET /api/vulnerabilities` puts the latest scans of an environment together, a finding both scanners made counted once, and leaves out the scans of images that are gone. With no `limit` it answers every finding, and with `limit=0` the counts alone. `severity`, `image`, `container` and `stack` each take several values with commas between, `image` and the rest matching a name whole; `q` matches a part of the CVE, the package, the image, a container or a stack, whatever its case. `sort` is `severity`, `cve`, `package`, `image`, `installed`, `fixed`, `container`, `stack` or `scannedAt`, anything else being no order, and by severity the gravest come first unless `dir` is `desc`. The `summary` counts what matched.
- **A finding names the containers made from its image as Dockhand last looked.** `containers` and `stacks` are worked out from what runs on the host and kept for half a minute, so a container started just now is not there yet.
- **Scanning everything reports image by image.** As a job, `POST /api/vulnerabilities/scan-all` has a `scanned` line for each image with what each scanner counted, and a result of `scanned`, `failed`, `total` and `cancelled`. An environment there is none of, and none at all, answer 200 with `success` false and why.
- **The exports are files.** `GET /api/vulnerabilities/export` writes an environment's findings as `json` or `csv`, narrowed as the list is; `GET /api/images/scan/export` writes one image's latest scan as `json`, `csv` or `sarif`, and wants the image's id: given a name, it answers a file with no findings in it.
- **Removing a scanner removes its image and its database.** `DELETE /api/settings/scanner` wants `removeImages=true` and `env` (400 without either, 404 for an environment there is none of), takes `scanner` to name one, and answers which it `removed`: none when the host had none. The environment's setting is left as it was. `DELETE /api/settings/scanner/cache` removes the database volumes on every environment and Dockhand's own copies, and lists the same names whether or not they were there.

### Users and the login

All of this was seen on a 1.0.51 server with no licence. What a licence changes could not be tried.

- **Every user is made an administrator, and without a licence that mark holds nobody to less.** `POST /api/users` answers 201 with `isAdmin` true whoever asks. `PUT /api/users/{id}` with `isAdmin` false sets the mark, and a user so marked was refused nothing in six tries with its own token: it made another user, changed the login settings, changed another user's record, reached a host's Docker, and marked itself an administrator again. Roles answer 403 `Enterprise license required`.
- **A user is changed a field at a time, and little is checked.** Only what is sent changes. An empty `email` or `displayName` is saved as null, which is how one is forgotten. An email that is no address is saved as it is, and so is an empty `username`, leaving a user with no name. A name in use answers 409, a password under 8 characters 400, and a user that is not there 404.
- **A new password ends sessions and not tokens; switching a user off ends both, and switching it on gives them back.** After `PUT` with a `password` the old one answers 401 at sign-in, the user's session cookie answers 401, and its API token still works. `isActive` false makes its token and its session answer 401 at once and its sign-in `Invalid username or password`; set true again, the same token works. Deleting a user deletes its tokens.
- **A token lists its own user's tokens, and can neither make nor revoke one.** `GET /api/auth/tokens` gives the tokens of the user the caller's token belongs to and nobody else's. `POST /api/auth/tokens` answers a token 403 `Token creation requires a session login, not a Bearer token`, and `DELETE /api/auth/tokens/{id}` 403 `Token management requires a cookie session`. Nothing tells a token whose it is.
- **Only the only user is guarded, and the way past that guard switches the login off.** Asked of the one user a server has, `PUT` with `isActive` false, `PUT` with `isAdmin` false and `DELETE` each answer 409 with `isLastAdmin` and a message that doing it will disable authentication. With `confirmDisableAuth` each is done, answers `authDisabled` true, and the login is off from then on.
- **With a second user, the last administrator is not guarded at all.** While a second user existed that was switched on and no administrator, the only administrator was switched off, unmarked and removed, each answered 200 with the login left on. With two administrators, one of them switched off, the other was switched off too: the login stayed on, no user was switched on, every caller was turned away and no call could undo it.
- **With the login off nobody is asked anything, and who is switched on or an administrator cannot be changed.** Every call is answered whatever is sent as a token, a token there is none of included. Anyone can make a user, change its name and details, and delete it. A `PUT` with `isActive` or `isAdmin` answers 200 with the record as it was: neither mark is changed for anyone. `GET /api/auth/tokens` and `POST /api/auth/login` answer 400 `Authentication is not enabled`.
- **The login can be switched on over a server nobody can sign in to.** `PUT /api/auth/settings` with `authEnabled` true answers 400 `Cannot enable authentication without any users` when there is no user at all, and 200 with any user, one that is switched off or no administrator included. Switched on with its only user switched off, the server turned every caller away and no call could undo it. The throwaway server was lost to this and to the bullet above, once each. The way back from a last administrator switched off has to be taken while the login is still off: make another user, switch the login on, sign in as that one, and switch the first back on.
- **A token outlives the login being off.** Switched off and on again, a token made before works as before.
- **A session's length is bounded without a word, and the default provider is not checked at all.** A `sessionTimeout` under 3600 is saved as 3600 and one over 604800 as 604800; 0 is saved, and means never. `defaultProvider` takes any text. What is offered at sign-in is `local` and `oidc:<id>` for each OIDC record that is switched on, and the setting goes on naming a record after it is deleted.
- **A licence is asked for by name and key.** `POST /api/license` answers 400 `Name and key are required`, and given both, `Invalid license format`. `DELETE /api/license` answers success with none to remove. What a valid licence answers could not be seen.

### Single sign-on

- **An OIDC record is not the Enterprise edition's, and nothing in it is checked.** `POST /api/auth/oidc` needs `name`, `issuerUrl`, `clientId`, `clientSecret` and `redirectUri`, answering 400 `Missing required field` for the first that is missing, and saves an issuer that is no address. A record is made switched off unless `enabled` is sent, with `scopes` `openid profile email`, `usernameClaim` `preferred_username`, `emailClaim` `email`, `displayNameClaim` `name`, `roleMappingsClaim` `groups` and no `adminClaim`. Two may share a name.
- **The secret never comes back.** Every answer has `clientSecret` as eight asterisks.
- **A change is a field at a time, and an empty text means a different thing for each field.** `adminClaim` and `adminValue` sent empty are saved as null. `scopes` and `usernameClaim` are saved empty. `roleMappingsClaim` goes back to `groups`. `name` is saved empty.
- **Switched on, a record is offered at sign-in at once.** `GET /api/auth/providers`, which needs no login, lists it as `oidc:<id>` beside `local`, and stops when it is switched off or deleted. With the login off it lists nothing.
- **Only a session may try one, and nobody signed in through one here.** `POST /api/auth/oidc/{id}/test` answers an administrator's token 403 `Admin access required` and the same user's session 200. There was no provider to sign in to, so what the claims of a record do when someone signs in, `adminClaim` among them, was not seen.

### Settings

- **The general settings are one flat record of 59, saved a key at a time.** `GET` and `POST /api/settings/general` both answer all of them. `POST` changes only the keys sent, passes over a key it does not have, and changes nothing for `{}`.
- **Nothing is refused, and what cannot be used is changed without a word.** A number found too small is raised: `eventRetentionDays` -5 to 1, `logBufferSizeKb` 0 to 100, `eventPollInterval` 0 to 30000, `metricsCollectionInterval` 1 to 10000, `scanRetentionKeep` 0 to 1. `logMaxLines` over 2000 is made 2000. `scanRetentionGraceDays` 0 is kept as 0. A word it does not know is passed over, for `eventCollectionMode` (which takes `stream` and `poll`), `labelFilterMode` and `downloadFormat`. `stackLogOperations` keeps the entries it knows and drops the rest, so a list of unknown words empties it.
- **`externalStackPaths` is a list, though the document says a text.** A text is passed over; a list is saved and answered. `primaryStackLocation` sent empty or null is forgotten.
- **A schedule it cannot read is saved, and the job it times then never runs.** `eventCleanupCron` saved as `not a cron` answers 200, and the job lists no next run until a schedule it can read is saved. The retention beside it is what the job goes by: with `eventRetentionDays` 1 the job described itself as removing container events older than 1 days.
- **A time zone it does not know is saved while the save is said to fail.** `defaultTimezone` with a zone there is none of answers 500 `Failed to save general settings`, and the setting is read back as that zone. While any of the schedules could not be read, a real zone got the same 500 and was saved too. An empty one is saved as `UTC`.
- **The settings for newer versions are replaced whole.** `POST /api/settings/semver` answers `{"success":true}` and sets all four: one left out goes to its default, `enabled` false, `maxBump` `major`, `matchFlavor` true, `includePrerelease` false, so changing one alone switches the detection off. `maxBump` takes `major`, `minor` and `patch`, and anything else is made `major`.

### Templates

- **The templates are other people's lists, fetched and kept for an hour.** A server comes with nine sources, two of them switched on, which between them gave 982 templates when asked: 634 of one image each and 348 that are a compose file in a repository. `GET /api/templates` gives them all, from every source that is switched on.
- **What was fetched from an address is kept with the name the source had then.** A list changed where it is served was not read again within the hour. A source renamed kept its templates under the old name, and an address removed and added again under another name listed its templates under the first.
- **A source is taken whatever its address answers.** `POST /api/templates/sources` refuses a text that is no address (400 `Invalid source URL`) and an empty name, and takes anything else: an address that answers nothing, or what is no list of templates, adds a source with no templates, and only the server's own log says why. Two sources may share a name and an address.
- **A source that is not there is answered as changed and as removed.** `PUT` and `DELETE /api/templates/sources` answer `{"ok":true}` for an id there is none of. `DELETE` removes one of the sources the server comes with like any other, and nothing makes one `builtin` again.
- **Switching a source off or on shows at once.** Its templates leave the list and come back with no wait.
- **A compose file is written from the template that is sent, not looked up.** `POST /api/templates/compose` with a template's id alone answers 500; with its `type`, `title` and `image` it answers a compose file of one service, named from the title, and writes in the `ports`, `volumes`, `env`, `restartPolicy` and `network` it is sent. A volume with no `bind` is written `undefined:/path`, which is no volume. A variable with no default is written empty. Sent `network` `host`, it writes `network_mode: host` and leaves the ports out.
- **A stack template's compose file is fetched from its repository each time.** One whose repository cannot be reached answers 500 `fetch failed`.

### Tags

- **A tag is a name, a colour and an icon, and Dockhand keeps no two whose names differ only by case.** `POST /api/tags` wants a name (400 `A valid tag name is required`) and takes the spaces off it. Asked for a name there is a tag of already, in any case, it answers 200 with the tag it has, unchanged, as though it had made one.
- **A tag is one of sixteen colours.** `slate`, `red`, `orange`, `amber`, `lime`, `green`, `emerald`, `teal`, `cyan`, `sky`, `blue`, `indigo`, `violet`, `purple`, `fuchsia` and `pink` are taken as asked. Any other, `yellow` or `#ff0000`, makes a new tag `slate` and leaves a tag that is changed the colour it was, each answered as done. The icon is whatever text it is given.
- **A change sets what it is sent.** `PUT /api/tags/{id}` answers `{"success":true}` and nothing of the tag. A name another tag has is refused whatever its case (409); an empty name is refused (400); an icon sent empty is forgotten. A tag there is none of is answered `{"success":true}`, changed or removed, though nothing was.
- **The tags of a container and of a stack are kept under its name on one environment, and not with the thing itself.** `PUT /api/container-tags/{name}?env=` and `PUT /api/stacks/{name}/tags?env=` take the whole list of a name's tags and save it for any name at all, one nothing has among them. A container that is renamed leaves its tags under the name it had, and a container or a stack that is removed leaves them under its name: whatever has that name next has them. The lists come back in an order of Dockhand's own, each tag once however often it was sent.
- **A change that names a tag there is none of takes every tag the name had.** It is answered 500 `FOREIGN KEY constraint failed`, and the name is read back with no tags: what it had is taken away before what was asked is given, and is not put back.
- **Removing a tag takes it from everything.** `DELETE /api/tags/{id}` answers `{"success":true}` and the tag is gone from every container and stack that had it, on every environment.

### Icons

- **An icon is a text Dockhand keeps for a container, a stack or an environment.** It is the name of one of Dockhand's own icons, `selfhst:` and a reference for one of selfh.st's, or `custom:` for a picture it was sent: `custom:container`, `custom:stack`, `custom:env-<id>.webp`. A name is not checked: one that is no icon's, of two words or of spaces alone is saved.
- **A container's and a stack's icon is kept under its name on one environment.** `POST /api/container-icons/{name}?env=` and `POST /api/stacks/{name}/icon?env=` take an `icon` or an `image`, the picture as a `data:` address, and answer 400 for neither; a picture wins over a name sent with it. A name no container has is given an icon all the same. For a container, an environment there is none of answers 500 `FOREIGN KEY constraint failed`. `DELETE` answers `{"success":true}` whether there was an icon or not.
- **A picture is kept as WebP whatever it was sent as.** PNG, JPEG, GIF and WebP are taken, and SVG and what is no picture are refused (400 `Uploaded file is not a recognised image`). One much larger than 300,000 characters as sent is refused (400 `Image too large`), an environment's just above that and a container's and a stack's somewhat later. The `GET` of each answers the picture as `image/webp`, and 404 for an icon that is a name.
- **An environment's icon is a field of the environment.** `PUT /api/environments/{id}` saves any `icon` text; `POST /api/environments/{id}/icon` takes a picture and, unlike the other two, takes anything at all as one: text is answered `{"success":true}` and kept. `DELETE /api/environments/{id}/icon` gives the environment the icon `globe`, whatever it had, a name included.
- **Giving a stack an icon makes Dockhand keep a record of it.** A stack it only found has none; given an icon it has one of `sourceType` `external` with no compose path, which stays when the icon is removed and goes only when the stack is removed. A name no stack has gets the same record, and `GET /api/stacks` then lists a stack of that name, `created`, with no containers.
- **A stack with such a record is not adopted by `POST /api/stacks/adopt`.** Given its name and its file, that call answers `adopted` with another name, the stack's with `-1` after it, and makes a second stack with the file and no containers, leaving the first without one. Saving the file where it lies, `PUT /api/stacks/{name}/compose` with its `content` and `composePath`, gives the record its file: it is `internal` from then on, with its containers as they were.
- **The icons of selfh.st come through Dockhand.** `GET /api/icons/selfhst-manifest` answers the list, some 2,900 of them, which Dockhand fetches from selfh.st and keeps a week. `GET /api/icons/selfhst/{ref}` answers one as SVG, WebP or PNG; a reference it has no icon for is answered 200 with a small SVG of nothing, and one that is no reference 400. `POST /api/icons/selfhst/batch` answers each of several that could be had and leaves the rest out.

### Labels of environments

- **A label is a word an environment has, and every change to labels goes through one call.** `POST /api/labels` takes an `action`: `add` (a `label` and `environmentIds`), `rename` (`oldLabel` and `newLabel`), `set-color` (a `label` and a `color`) and `delete` (a `label`); any other is refused (400), and so is one with what it needs left out. `GET /api/labels` lists each label with the environments that have it, a count of them, and its colour.
- **Labels differ by their case.** `prod` and `Prod` are two labels, and one environment may have both. A label given or renamed has the spaces taken off it; the label a rename or a removal names is matched as it is written.
- **A label given to an environment there is none of is passed over.** `add` answers how many environments it `affected`: one that has the label already, and one that is no environment of the server's, are not counted and not refused.
- **Renamed to the name it has, a label is taken from every environment.** `rename` with the same `oldLabel` and `newLabel` answers that it affected every environment that had the label, and none has it afterwards, nor its colour.
- **Renamed to the name of another label, the two are one.** Every environment that had either has the one, with the colour of the label it joined when that had one and its own colour otherwise. A label there is none of is answered as renamed on no environment.
- **A colour is `#` and six hexadecimal digits, and anything else takes the colour away.** `set-color` keeps `#12AbCd` as it is written. `red`, `#abc`, `123456`, an empty text and no colour at all are each answered `{"success":true}` and leave the label with no colour.
- **A colour outlasts its label.** A label taken from its last environment by saving the environment without it (`PUT /api/environments/{id}` with its `labels`) keeps its colour: `colors` in the answer of `GET /api/labels` still names it, and `labels` does not. A colour can be set for a label no environment ever had. `delete` clears it, answering that it affected none.

### Config sets

- **A config set is kept, and nothing in the API applies one.** It holds `envVars` and `labels` (each a list of `key` and `value`), `ports` (`hostPort`, `containerPort`, `protocol`), `volumes` (`hostPath`, `containerPath`, `mode`), a `networkMode` and a `restartPolicy`. No other call of the API takes a config set or names one.
- **Only the name is checked.** `POST /api/config-sets` answers 201; it refuses a set with no name (400 `Name is required`) and a name another set has, letter for letter (400 `A config set with this name already exists`): a name in another case is another set. Everything else is saved as it comes: a variable with no name, a name held twice, a port that is no number, a protocol, a mode, a network mode and a restart policy that are none. Given a name alone, a set is `bridge` and `no` and holds nothing.
- **A change sets what it is sent and keeps the rest.** `PUT /api/config-sets/{id}` answers the whole set. A list sent empty takes everything of its kind away, a description sent empty is forgotten, and a name sent empty is saved as empty. A set there is none of is answered 404, read, changed or removed.
- **Values are given back as they were sent.** A password or a token put in a variable is read back in full by whoever may read config sets.

### What the web interface remembers

- **Whose they are.** With the login on, the order of environments, the order of tags, the sidebar, the columns of a grid and `hideSystemJobs` are kept for the user who asks, a token's user among them: a second user who signs in reads none of what the first saved. The dashboard, the favourites of the log view and the two pages set for everyone are one set, the same whoever asks. With the login off there are no users, and each is the one set there is.
- **An order is a list of numbers, kept as it is given.** `POST /api/preferences/environment-order` and `/api/preferences/tag-order` take `{"order":[…]}` and answer it. A number no environment or tag has is saved with the rest, and a tag that is removed stays in the order. A number given twice is refused (400 `order must not repeat an environment id`). An empty list is no order, and so is `DELETE`, which answers `{"order":[]}`.
- **The sidebar needs both of its lists, and takes any text in them.** `POST /api/preferences/sidebar` with `order` and `hidden` answers both; one left out is refused (400 `hidden must be an array of strings`). Two empty lists, or `DELETE`, put it back as it comes.
- **The columns of a grid are kept under any id.** `POST /api/preferences/grid` needs a `gridId` and `columns` (400 `columns array is required`), saves any text as the id of either, and answers every grid. `DELETE` with `gridId` forgets that grid, and with none forgets them all.
- **The dashboard is changed a field at a time.** `POST /api/dashboard/preferences` sets what it is sent of `locked`, `viewMode` and `gridLayout` and answers all three. Any text is saved as a `viewMode`, where the page has `grid` and `list`. Any list of records is saved as a `gridLayout`, where the page saves an `id`, `x`, `y`, `w` and `h` for the tile of each environment, by the environment's number; a `gridLayout` that is no list is passed over without a word.
- **The two pages are checked, and forgotten with a null.** `PUT /api/settings/navigation` sets `landingPage` and `envClickPage`, either alone or both, for `scope=global` or with no scope named. The opening page is one of `dashboard`, `containers`, `stacks`, `logs`, `images`, `volumes`, `networks`, `schedules`, `activity` and `terminal`, and the page a click on an environment opens is any of those but `dashboard`; anything else is refused (400 `Invalid landingPage`, `Invalid envClickPage`). A page sent as `null` is forgotten, and with none set `effective` is `dashboard` and `containers`. The generated client leaves an empty field out, so `ForgetNavigationPages` is written by hand to send the null.
- **A user's own pages and profile are for a browser that signed in.** `PUT /api/settings/navigation?scope=user` sets pages that are in effect for that user alone, over the ones set for everyone. Asked with a token it answers 401, as `GET /api/profile` and `GET /api/profile/preferences` do, and on a server with its login off each answers 400 `Authentication is not enabled`.
- **The favourites of the log view are one list for each environment.** A container is a text in it, by its name, and a group a record of its `name` and `containers`. `GET /api/preferences/favorites` and `GET /api/preferences/favorite-groups` both answer the whole list, as every change to either does. `add` and `remove` on the first take a `containerName`, and any text is kept, once however often it is added. A group needs a name (400 `Group name is required`), one no other group of the environment has (400), and a container (400 `Containers array is required and must not be empty`); `update` renames it and sets its containers where it stands (404 for one there is none of), and `remove` takes it out. An environment has to be named to read them (400 `Environment ID is required`), and one there is none of cannot keep any (500 `Failed to update favorites`).
- **Reordering either kind drops the other.** `reorder` on the favourites call replaces the whole list with the names it is sent, so every group is gone, and `reorder` on the groups call replaces it with the groups it is sent, so every name is. The favourites call takes names and groups together all the same, which is how both are kept: `SetLogFavorites` is written by hand to send such a list, since the document declares a list of names.

### Secret providers

- **A provider is a store outside Dockhand that a stack's secrets are loaded from.** The document names four kinds; a 1.0.51 server takes `vault`, `infisical`, `doppler`, `op-connect`, `op-service-account`, `azure-kv`, `bitwarden` and `keepass`, letter for letter in that case, and refuses any other: 400 `Unknown secret provider type` on a save, and a 200 saying `A valid provider type is required` on a test. Its `config` is whatever that kind needs: for `vault` an `address` and a `token`, with a `mount` when the secrets are not under `secret`, and a `namespace`. A setting it does not know is saved and given back with the rest.
- **What it signs in with is kept and never given back.** `GET /api/secret-providers` lists each by `id`, `name` and `type` with when it was made and changed; `GET /api/secret-providers/{id}` adds its `config` without the token, and `stacksUsing`, each stack by its name and its environment's number. `updatedAt` is written as `2026-10-11 03:22:58` until the provider is changed and as `2026-10-11T03:25:22.481Z` after.
- **Trying one always answers 200.** `POST /api/secret-providers/test`, for one that is not saved, and `POST /api/secret-providers/{id}/test`, for one that is, answer `ok` and, when that is false, an `error` in the store's own words: `Address is empty`, `Vault returned 403: permission denied`, `getaddrinfo ENOTFOUND` and the host. A saved one is tried with the `config` sent in place of the saved one, whole. The saved token is used when none is sent and the address is the saved one; when the address differs it is refused, `You changed the host or address, so enter its credential to test`.
- **Saving checks the name and the kind, and nothing else.** `POST` answers 201. A name is required and trimmed, and is another's only letter for letter (400 `A secret provider with this name already exists`). A provider Dockhand cannot reach is saved all the same.
- **A change replaces the settings whole and keeps the token, wherever the settings now point.** `PUT /api/secret-providers/{id}` sets the `name`, `type` and `config` it is sent, and `{}` changes nothing. An empty name (400 `Name cannot be empty`) and a kind there is none of are refused; a kind the settings are none of is saved. A `config` sent replaces the saved one, but for the token, which is kept when none is sent: moved to another address with no token given, the provider signs in there with the token it had. The test call refuses exactly that, and the save does not.
- **What it holds is asked by path, and only names come back.** `POST /api/secret-providers/{id}/probe` with a `selector` answers `bulkKeys`, the names of the keys there. For `vault` the selector is a path under the mount, read as KV v2, and a path nothing is at answers `ok` false and `KV v2 path not found`. With no selector it answers `ok` and no keys. `refs` were not seen resolved by a `vault` provider, whatever was sent.
- **The default is what the web interface offers, and no more.** `GET` and `PUT /api/secret-providers/default` answer `providerId`, null for none. `{}` or a null clears it, and a provider there is none of is refused (400). A stack made through the API with no provider named has none, whatever the default.
- **A stack is bound by a number, and names its path in its `.env` file.** `secretProviderId` on `POST /api/stacks` and on `PUT /api/stacks/{name}/compose` binds a stack. A save that leaves it out keeps the binding, a null clears it, and a number no provider has answers 500 `FOREIGN KEY constraint failed`. The generated client leaves a 0 out, so `ForgetStackSecretProvider` is written by hand to send the null. The path whose every key is loaded is the variable `DOCKHAND_SECRET_SELECTOR` among the stack's variables.
- **A stack says where its secrets come from, and what its last deploy was given.** `GET /api/stacks/{name}/env` answers the provider's `type` and `name` as `secretProvider`, and `injectedSecretKeys`: the names the last deploy was given, empty before one and still there after the stack is taken off its provider. `GET /api/stacks/sources` answers the provider's number. `POST /api/stacks/{name}/env/validate` knows nothing of a provider and counts each variable it gives as missing.
- **A deploy loads the secrets, or fails.** Each key at the path is given to compose as a variable of that name. With the provider out of reach the deploy answers 200 `{"success":false,"error":"Failed to deploy compose stack"}`, and what was running is left as it was.
- **Removing a provider takes its stacks off it without a word.** `DELETE /api/secret-providers/{id}` answers success whatever uses the provider. Each stack's binding is cleared, as is the default when it was that one, and the next deploy of such a stack succeeds with every variable the provider gave empty.
- **A provider there is none of is a 404,** read, changed, tried, asked what it holds or removed.

### Git

- **Three things are kept: credentials, repositories, and git stacks.** A credential is what Dockhand signs in to a git server with. A repository is an address, a branch and a credential, and belongs to no environment. A git stack is a compose stack on one environment that is deployed from a repository. Everything about deploying is the git stack's: the document says as much of repositories, which still answer the fields of an older arrangement.
- **A credential's password and key are kept and never given back.** `authType` is `none`, `password` or `ssh`, and any other is refused (400 `Invalid auth type`). `password` wants a password and `ssh` a key (400 for either missing), and no user name is asked for. The key is any text at all: `not a key` is saved. The list and a read answer `hasPassword` and `hasSshKey` and nothing of either. A name is required, is another's only letter for letter (400 `A credential with this name already exists`), and is kept with the spaces it was sent with. A change sets what it is sent and keeps the rest, so one switched to `none` still keeps its password.
- **Removing a credential that repositories use is not refused.** `DELETE /api/git/credentials/{id}` answers success, and each repository fetched with it is left with `credentialId` null, to fail at its next fetch if it asks for a login.
- **Trying a repository always answers 200 once git has been asked.** `POST /api/git/repositories/test`, for one that is not saved, and `POST /api/git/repositories/{id}/test`, for one that is, answer `success` with the `branch` and its `lastCommit`, or an `error` in git's own words: `Branch 'x' not found. Available branches: main, next`, `could not read Username for 'http://host': terminal prompts disabled` for one that asks for a login it was not given, `repository '...' not found`. No address is a 400 and a credential there is none of a 404. `POST /api/git/branches`, by `repositoryId` or by `url` with a `credentialId`, lists each branch with its newest commit, and answers 500 for a repository it cannot ask.
- **A repository is saved whatever it is.** `POST /api/git/repositories` wants a name and an address and takes `main` for a branch unless one is said. One that cannot be fetched, on a branch that is not there, is saved all the same. A name is another's only letter for letter, and name, address and branch are kept with the spaces they were sent with. A change sets what it is sent; `credentialId` null takes the credential away, which the generated client cannot send, so `ForgetGitRepositoryCredential` is written by hand. An address with a password in it, `https://user:password@host/...`, works and is given back whole to whoever lists the repositories.
- **`POST /api/git/preview-env` reads the variables a repository's `.env` files hold.** It fetches the repository into a folder of its own, reads the `.env` beside where `composePath` says the compose file is and the file named as `envFilePath`, answers `vars` and, for each, which file it came from in `sources` (`.env` or `envFile`), and removes the folder. The compose file itself is not looked for: a path to none answers the same.
- **A repository's own fetch, deploy and webhook are leftovers.** `GET` and `POST /api/git/repositories/{id}/sync` keep a copy of the repository under `git-repos/repo-<id>` that no git stack uses, and say whether that copy is behind. `POST /api/git/repositories/{id}/deploy` runs `docker compose -p <the repository's name> up -d` with no host named, which is the Docker that Dockhand itself is on; a Dockhand with no Docker socket of its own answers 200 with `success` false. `GET` and `POST /api/git/webhook/{id}` answer 403 `Webhook is not enabled for this repository`, and nothing in the API switches it on. The tools have none of these.
- **A git stack is made from a repository, and is a stack from then on.** `POST /api/git/stacks` wants a `stackName` in lower-case letters, digits, hyphens and underscores, an `environmentId` and a `repositoryId`, or in the repository's place a `url` with a `branch`, a `credentialId` and a `repoName`, which saves a repository with the stack. It takes the compose file's path (`compose.yaml` unless said), an extra `.env` file, a branch of its own, the schedule, the webhook, the four switches of a deploy, a `secretProviderId` and `envVars`. A name Dockhand already keeps a stack under on that environment is refused (409). Left with no `environmentId` it is made with none, and one there is none of answers 500. A webhook switched on with no secret is refused (400) unless the server was started with `ALLOW_WEBHOOKS_WITHOUT_SECRET=true`. With `deployNow` it deploys at once and answers the record with `deployResult`.
- **Made and not yet deployed, it is already listed.** `GET /api/stacks` gives it as `created` with no containers and `GET /api/stacks/sources` as `git`, while `GET /api/stacks/{name}/compose` answers 404 until its first deploy. Its record says `syncStatus` `pending`, then `synced` or `error` with `syncError`.
- **Each deploy fetches the repository and copies it over the stack's files.** The compose file and what lies beside it are copied to the stack's own folder, files gone from the repository are removed from there, and compose is run. So a compose file or `.env` saved for a git stack through the ordinary stack calls is accepted, and is replaced at the next deploy. `POST /api/git/stacks/{id}/deploy-stream` as a job reports as it goes (`Connecting to repository...`, the files added, updated and removed, each line compose prints as `logLine`) and ends with `status` `complete` or `error`. `POST /api/git/stacks/{id}/deploy` waits and answers `success`, `output`, the `command` and its `exitCode`. The first deploy makes every container afresh. A deploy that fails answers 200 with `success` false, leaves what was running, and has by then replaced the stack's files.
- **The four switches are compose's.** `buildOnDeploy` adds `--build`, `repullImages` `--pull always` and `forceRedeploy` `--force-recreate`; `noBuildCache` adds nothing to that command. `forceRedeploy` also has the schedule and the webhook deploy when nothing in the repository changed.
- **A fetch alone hides a commit from the schedule and the webhook.** `POST /api/git/stacks/{id}/sync` brings Dockhand's copy to the newest commit and answers what changed and what a deploy would remove (`deletionPlan`), without touching the stack's files or what runs. The record's `lastCommit` is then the new commit, while `syncedFiles` still names the commit the stack's files were taken at. The schedule and the webhook compare against the first: after a fetch alone both answer `No changes detected, skipping redeploy`, and the stack goes on running the old commit until it is deployed outright.
- **A webhook takes its secret and no login.** `GET /api/git/stacks/{id}/webhook?secret=` and `POST` to the same path, with the secret as GitLab's `X-Gitlab-Token` or signed as GitHub signs (`X-Hub-Signature-256`), deploy the stack for a caller with no session and no token: a wrong secret is a 401, a webhook that is off a 403. With nothing new it answers `skipped` true. The secret is given back whole by every call that answers the stack.
- **Its schedule is a cron, and any text is saved for one.** `autoUpdate` with `autoUpdateCron` puts the stack among `GET /api/schedules` as a `git_stack_sync`, which fetches it and deploys what changed; run before its time, it deploys a stack never deployed. `autoUpdateSchedule` is a word kept beside the cron and decides nothing. A cron that is none is saved, and the schedule then has no next run.
- **The variables Dockhand keeps for a git stack are not all secrets.** `envVars` on a make or a change, and `PUT /api/stacks/{name}/env`, keep variables for the stack in Dockhand's database, each a secret or not, and each deploy gives them to compose over the repository's own `.env`. Sent any, the list replaces the one kept, an empty list removes them all, and a secret sent back as `***` keeps its value. The path a secret provider is read at is one of them, `DOCKHAND_SECRET_SELECTOR`, where an ordinary stack keeps it in its `.env` file.
- **A change keeps what it is not sent, and checks little.** `PUT /api/git/stacks/{id}` saves a branch the repository does not have and a compose path that is not there, and each is said at the next fetch: `Branch 'x' not found in repository` when it is tried, `Compose file not found: x` when it is fetched. A branch, an extra `.env` file, a folder and a secret provider are taken away by a null, which the generated client cannot send, so `ForgetGitStackSettings` is written by hand; a webhook's secret goes only with the webhook off. A `repositoryId` sent is passed over without a word: a git stack stays with the repository it was made from.
- **A rename is done in three steps, and a refusal comes after the first.** `stackName` on a change renames the git stack, then the stack's record, then its variables. A stack with containers is renamed all the same: the containers stay under the old name with nothing deploying them, and the next deploy makes a second set under the new one. A name another stack has is refused with a 400 once the git stack itself has been renamed, so the git stack then carries the other stack's name; the next rename moves that other stack's record and variables, its secret provider among them, to the git stack. Either way the stack's folder and Dockhand's copy of the repository stay on its disk under the old name, and a git stack later made under that name starts from the copy: its `.env` files are listed before it was ever fetched.
- **Forgetting a git stack leaves its containers.** `DELETE /api/git/stacks/{id}` removes the git stack, its schedule, Dockhand's copy of the repository and the variables kept for it, and answers success. Its containers go on running and its files stay in the stack's folder; it is then a stack Dockhand only found. `DELETE /api/stacks/{name}` is the other way to remove one: the containers and files go, and the git stack with them.
- **Removing a repository takes its git stacks with it.** `DELETE /api/git/repositories/{id}` is not refused for one git stacks are made from: each of those git stacks is removed with it, its containers left running, and the stack's record stays behind as a `git` stack that no longer is one.
- **A git stack on the agent's host is deployed like any other.**
- **A credential, a repository and a git stack there is none of is a 404** for every call but a make, where a repository there is none of is a 400.

### Backups

Seen on 1.0.51 started with `FEAT_BACKUPS_ENABLED=true`, with restic's own REST server for a repository. Dockhand's changelog calls the feature a beta.

- **A backup runs on the Docker host, not in Dockhand.** Dockhand has restic of its own, which it tries a destination, makes a repository and reads snapshots with. A backup and a restore run in a helper container on the host (`dockhand-backup-<config>-…`, `dockhand-restore-<snapshot>-…`, from the image the setting `defaultBackupImage` names, which the host pulls the first time). So a repository has to be one the host's containers reach: one only Dockhand reaches is saved and tried without complaint, and a backup to it retries for many minutes until it is stopped.
- **A destination is a restic repository.** `repository` is a folder's path, or opens with `rest:`, `s3:`, `b2:`, `azure:` or `gs:`; anything else is a 400 `Invalid repository`, and an address of the server itself or of a cloud's metadata service a 400 `Repository host not allowed`. The password is never given back. `envVars`, what the store is signed in to with, is given where one destination is read, made or changed and left out of the list. `policies` is JSON written out as text. `flags` is JSON written out as text too, holding the flags of a backup and of a restore, which `backupFlags` and `restoreFlags` give apart; a flag is checked against a list (400 `Disallowed restic flag`).
- **Trying one cannot tell an empty place from one nobody is at.** `POST /api/backup/destinations/test` answers `{success: false, needsInit: true, error: "Repository not initialized"}` to a server with no repository yet and to a name nothing answers at alike. A wrong password is `{success: false, error: "Fatal: wrong password or no key found"}`.
- **A destination is saved whether or not it can be used.** `POST /api/backup/destinations` makes the repository when there is none, and answers 201 with a wrong password, or an address nothing is at, all the same: only `lastTestStatus` (`failed`) and `lastTestError` say so, on the next read. `PUT` saves a new address or password untried, and `lastTestStatus` goes on reading `success`. A `PUT` of `policies` or of `envVars` replaces the whole of what was kept.
- **Removing a destination removes every configuration kept in it**, with their schedules, and says nothing of them. The repository itself is not touched.
- **A configuration is saved unchecked.** A target no container has, a `type` that is neither `container` nor `stack`, no environment at all, a volume there is none of, and the same target twice are each a 201. An environment or a destination there is none of is a 500 `FOREIGN KEY constraint failed`. `selectedVolumes`, `retention`, `options` and `tags` come back as JSON written out as text.
- **Changing a configuration changes more than was asked.** A `PUT` keeps what it is not sent, but for what is kept: a body with a `schedule` and no `retention` has Dockhand write its own (`keepDaily` 7, `keepWeekly` 4, `keepMonthly` 6), and a configuration with a schedule cannot be saved with none; with no schedule, a `retention` of null, `{}` or all zeros is none. A schedule given to a configuration that had none switches it on whatever `enabled` says, and the same body again is then taken. A schedule is cleared by sending it empty.
- **A run, a restore, a verify and a task answer two ways**, as the other slow calls do: a caller that asks for JSON alone is made to wait and answered how it went, and any other is answered `{jobId}`. A run that fails is a 200 with `status` `error` and a `code` (`VALIDATION`, `RESTIC`, `UNKNOWN`); one that was stopped ends `skipped` with the `reason` `Backup cancelled`. What restic finds wrong in a repository is a 200 with `success` false.
- **The reads of a snapshot answer failures as a 200.** A snapshot there is none of is `{"error": "snapshot not found for this installation"}` from the browse, the metadata, the diff and the preview, and the list of a destination there is none of is `{"error": …}` where a list is declared. A folder a snapshot does not have reads as an empty one. A file fetched with `download` fails as a 500.
- **A snapshot holds `/volumes` and `/metadata`.** Each volume is a folder under `/volumes`; a stack's own files are the volume `__dockhand_stackdir__`. `/metadata/metadata.json` is what Dockhand wrote down of the container or stack, which `GET …/metadata` gives with the container's variables and labels taken out, and of a stack's secrets their names alone.
- **A stack is backed up from its folder on the Docker host.** Dockhand looks for it where it keeps the stack itself (`/app/data/stacks/<environment>/<stack>`) or, behind an agent, where the agent keeps it (`/data/stacks/<stack>`), and a run fails with `STACKDIR PROBE FAILED` when the host has nothing there. `GET /api/backup/stack-dir-listing` says beforehand: `kind` `listed` with what is there, or `unknown` with why.
- **A restore to somewhere else makes the container again unless told not to.** `mode` `in-place` wants `confirmOverwrite` and replaces each volume whole; any other word is a restore to somewhere else, which wants a `targetPath` (a folder on the host's own disk, each volume under `volumes/<name>`) or `volumeDestinations`. `postRestore` is `none`, `start` or `recreate`, and left out it is `start` in place and `recreate` elsewhere: a second container, made from the snapshot's record and run on what was restored. Any other word is read as left out. A volume that is already there is not restored into (`status` `error`, `already exists on the target environment`).
- **Upkeep is schedules of its own.** A configuration with a schedule is listed among the schedules as `backup`, and a destination's prune, check and verify as `repo_prune`, `repo_check` and `repo_verify`, numbered 100000, 200000 and 300000 above the destination's own number.
- **From 1.0.52 a destination can be an SFTP server, which this client cannot make.** `sftp:` is then a kind of address, tried and saved with an `sshPrivateKey` and `sshKnownHosts` and refused without (400 `SFTP destinations require an SSH private key`), and a destination's record says whether it has them (`hasSshPrivateKey`, `hasSshKnownHosts`). The 1.0.51 document has neither field. The live suites run on the newest Dockhand, 1.0.53 when this was written, and pass there.

### Stacks

- **A compose project Dockhand did not make is listed as a stack**, by its compose project label, with its containers.
- **Acting on a stack answers one of two ways, by what the caller says it accepts.** To a caller that will take anything, stopping, starting, restarting and deploying a stack answer `{"jobId"}` at once, and how it went is read from `GET /api/jobs/{id}`: `status` is `running` and then `done`, and `result` holds `success` with `output` or `error`. To a caller that asks for JSON alone (`Accept: application/json`) the server does the work first, ten seconds for a stop, and answers the result itself: `{"success":true,"output":"stop completed for 1 container(s): ..."}`.
- **What the server takes for "JSON alone" is a plain reading of the header.** It does the work first when `Accept` holds the text `application/json` and does not hold `text/event-stream`, wherever in the header and whatever weight either is given: `application/json, */*;q=0.1` and `application/json; charset=utf-8` are both JSON alone, `application/json, text/event-stream;q=0.9` is not, and nor is `Application/JSON`, since the reading minds capitals. No `Accept` at all is a caller that will take anything.
- **The dashboard's stream of statistics chooses the same way, and has nothing for a caller that asks for JSON.** `GET /api/dashboard/stats/stream` answers `text/event-stream` to a caller that names it or will take anything: an `environments` event at once, then each host's numbers, then `done`, and the server ends the stream itself. Asked for JSON alone it gathers for a second or two and answers `{"success":false,"error":"No result"}` with HTTP 200. The other six streams answer events whatever they are asked with.
- **A stream says hello first.** The activity feed, an environment's Docker events, a container's log stream, the merged logs and the schedules each open with a `connected` event the moment they are asked. The stream of container statistics sends nothing, its headers included, until its first sample a second or two later, and on a host with no containers answers `done` at once and ends.
- **An action that fails answers 200.** A stack that does not exist is `{"success":false,"error":"No containers found for stack \"...\""}` with HTTP 200, as a job or as a result, so how an action went is known only from `success`.
- **Taking down a stack Dockhand did not make only stops it.** `POST /api/stacks/{name}/down` on such a stack answers `stop completed for 1 container(s): ...`, and its containers are left there, exited: with no compose file to take down, Dockhand stops what it finds.
- **A stack Dockhand did not make can be stopped, started and restarted, and not deployed.** Deploying one fails in its job with `Stack compose file location not configured`, and reading its compose file answers 404 with `needsFileLocation: true`: Dockhand has not been told where the file is.
- **`GET /api/stacks/{name}` is not a call**: it answers 405.
- **Dockhand has a stack's compose file or it does not, and `GET /api/stacks/sources` says which.** It answers a record for each stack Dockhand has a file for, `sourceType` `internal` (or `git`) with the file's path, and nothing for a stack it only found running, until that stack is given an icon: then it has a record too, `sourceType` `external` with no path, which stays when the icon is removed. A stack it made is kept at `<base path>/<environment's name>/<stack>/compose.yaml`, the base path being `/app/data/stacks` in the image; one it adopted is `internal` as well, with its file wherever it lay. `envVarCount` counts the variables in the `.env` file and the secrets together.
- **Making a stack starts it unless told not to, and answers two ways like the actions.** `POST /api/stacks` with `start` left out brings the stack up; a caller that does not ask for JSON alone is answered `{"jobId"}`. A stack made and not started is listed with status `created` and no containers. Saving a compose file with `restart` set chooses the same way.
- **A name that is taken is taken over.** `POST /api/stacks` with the name of a stack Dockhand has answers `success` and replaces its file; with the name of a stack it only found, Dockhand now has a file for that stack, and the next deploy replaces its containers with what the new file says. With no `env` at all it answers `success` and makes a stack that belongs to no environment, which no call can then remove; with an `env` there is none of it answers 500 `FOREIGN KEY constraint failed`.
- **A compose file that does not parse is saved all the same.** Making a stack from one answers 200 `{"success":false,"error":"failed to parse ..."}` and the stack is kept, with the file; it cannot be deployed, and removing it answers 400 with the same parse error unless `force` is given.
- **A stack's variables are in two places.** The ones that are no secret are the lines of its `.env` file, read and written whole through `/env/raw`; saving it empty removes the file (`deleted: true`), a body with no `content` is a 400, and so is content that holds `***` as a value. The secrets are kept by Dockhand, encrypted, through `PUT /api/stacks/{name}/env`. `GET /api/stacks/{name}/env` lists both, a secret's value always `***`.
- **Saving secrets replaces them all, and a hidden value is kept.** `PUT /api/stacks/{name}/env` keeps the secrets it is sent and drops any it is not; one sent back with the value `***` keeps the value it had. A variable sent there that is no secret is stored and then neither listed nor used, so the `.env` file is where those go.
- **The variable check knows only what it is told.** `POST /api/stacks/{name}/env/validate` with no `variables` holds the file against the variables Dockhand keeps itself and counts the ones in the `.env` file as missing; given `variables`, a list of names, it holds the file against those, and an empty list is none. It answers `required`, `optional` (the ones with a fallback), `missing` and `unused`.
- **The compose check runs for any name and with no host.** `POST /api/stacks/{name}/validate` answers `findings`, each with a `ruleId`, a `severity` (`error`, `warn` or `info`), and usually a `service`, a `line`, a `message` and a `hint`. Given an `env` it also holds container names against the containers on that host (`CONTAINER_NAME_COLLISION`, an error), and `existing: true` says the stack's own containers are no clash.
- **A deploy is recorded as a run, and the record outlives the stack.** `GET /api/stacks/{name}/deploys` lists them, newest first, with `status` `success` or `failed`, `duration` in milliseconds, and for a failed one everything compose printed as `errorMessage`; `/deploys/{runId}/log` is what compose printed, as plain text. Removing the stack leaves its runs, and a stack made again under the name has them. `DELETE /api/stacks/{name}/deploys/{runId}` removes one and its log.
- **A deploy that fails answers 200 and leaves what was running.** Waited for, it answers `{"success":false,"error":"..."}` with compose's output as the error; the containers that ran go on running.
- **Through an agent, a deploy can be recorded with no summary and no log.** When a stack's name contains the value of one of the variables in its `.env` file, a stack named `app-staging` with `MODE=staging` say, the deploy succeeds and its run has `summary: null` and a log that answers 404 `Log not found`. The same stack on a host reached by its socket is recorded in full. Through an agent a run's summary is otherwise there with every count zero.
- **A restart can make the containers again.** `POST /api/stacks/{name}/restart?mode=recreate` on a stack Dockhand has the file of makes each container anew, as a deploy told to recreate does; any other `mode`, or none, restarts the ones there. On a stack Dockhand only found, every mode restarts.
- **Taking down keeps the file.** `POST /api/stacks/{name}/down` removes the stack's containers and the networks it made and leaves it listed as `created`; `removeVolumes` removes its named volumes too. Taken down again it answers `Stack "..." down completed successfully`.
- **Removing a stack removes its containers, and what else goes depends on how Dockhand has it.** `DELETE /api/stacks/{name}` on a stack kept in Dockhand's own directory removes the containers, the networks, the directory with its files, the secrets and the record, and keeps named volumes unless `volumes=true`; `files=false` leaves the files on disk, and Dockhand forgets the stack all the same. On a stack whose files are elsewhere, adopted or moved, the files are never removed. On a stack Dockhand only found it removes the containers one by one and nothing else, not the volumes even when asked, and answers 400 for a running one unless `force` is given. There is no way to have Dockhand forget a stack and leave its containers. Removing a name there is no stack of answers `{"success":true}`.
- **What removing would take can be asked first.** `GET /api/stacks/{name}/delete-preview` answers the stack's named volumes, read from the host, its directory, and `canDeleteFiles`, which is false for files outside Dockhand's own directory; for a name there is no stack of it answers with nothing in it and a 200.
- **Looking for compose files looks inside Dockhand's own container.** `POST /api/stacks/scan` with a `path` answers each folder under it that holds a compose file as `discovered`, with `runningOn` naming the environments a compose project of that folder's name already has containers on, and the ones Dockhand has already as `skipped`. A path on a Docker host is `Path does not exist` unless the folder is mounted into Dockhand. With no `path` it looks through the folders named in the settings. Nothing is saved by looking.
- **Adopting gives Dockhand a file where it lies.** `POST /api/stacks/adopt` takes names with compose paths and an environment, and answers the ones `adopted` and the ones `failed`, each with why; nothing running is touched. The `.env` beside the file is read as the stack's own.
- **Moving a stack's files writes over what is there.** `POST /api/stacks/{name}/relocate` moves the compose file and its `.env` to another folder and has Dockhand deploy from there; a file of the same name already in that folder is replaced without a word, and `check-path-change`, which says how many files would move, does not say so. `POST /api/stacks/validate-path` tells a folder that is there (`valid: true`) from one that is not (`Path does not exist`) and from a file (`Path is not a directory`).
- **Dockhand says where a new stack's files would go.** `GET /api/stacks/default-path` with `name` and `env` answers `stackDir`, `composePath` and `envPath`, under a folder named for the environment, and making the stack puts the file there. An `env` there is none of is left out of the path without a word, and `name` is not checked.

### Images

- **An image is told apart by its id alone.** Its history, a new name for it and its removal all take the `sha256:` id in the path. A name with a slash in it, which is most names, answers 400 `Invalid image ID`; a name with none is passed to Docker and answers 500 when there is no such image.
- **An image is removed whole.** `DELETE /api/images/{id}` removes the image and every name it goes by: there is no call that takes one name off an image. Under more than one name it answers 409 `must be forced` until `force=true` is sent. One a running container was made from answers 409 `it is being used by a running container` forced or not; one only stopped containers were made from goes when forced.
- **A pull that fails answers 200.** Waited for, `POST /api/images/pull` answers `{"status":"complete"}` or `{"status":"error","error":"..."}`, the second for an image there is none of, an environment there is none of and no environment at all alike. Docker's own words come inside the error as the JSON they were sent in.
- **Giving an image a name another has takes it from the other**, as `docker tag` does, with no word of it in the answer.
- **Pruning images takes only the nameless unless told.** `POST /api/prune/images` with nothing said, and with `dangling=true`, removes images with no name left; `dangling=false` removes every image no container was made from, and also takes a spare name off an image that is in use under another. An image a container was made from, running or stopped, is never taken. Its failures answer 200 with `success` false and `error`; the other prune calls answer 500.
- **Looking inside a volume has the host pull `busybox:latest`.** The file browser runs a helper container from it, kept until it is released, and a prune of every unused image then takes that image with the rest.
- **An image is written out by its id alone.** `GET /api/images/{id}/export` answers the image as a tar archive, as `docker save` writes one, or gzipped with `compress=true`; `tag` picks which of the image's names the archive records and is called after. A name in place of the id is refused (400 `Invalid image ID`), and an id no image has is Docker's own refusal as a 500. It works for a host behind an agent as for any other.
- **An image is loaded from the raw archive, onto a host Dockhand reaches itself.** `POST /api/images/load` takes the tar as its body, plain or gzipped, and answers `success` with what Docker printed, `Loaded image:` and the name. A host behind a Hawser agent is refused, 500 `Uploading an image tar is not supported on Hawser connections yet`. What is no archive is not loaded: a 500 in Docker's words, or a connection dropped before any answer.

### Volumes

- **A volume's list names who mounts it, stopped containers too**, under `usedBy`, by id and name and with no state. A volume a container mounts answers 409 `volume is in use` to its removal, and is left by a prune.
- **Pruning volumes takes named ones.** `POST /api/prune/volumes` removes every volume no container mounts, where `docker volume prune` has left named volumes alone since Docker 23.
- **Making a volume that is there answers as made.** `POST /api/volumes` with a name the host has a volume under answers `{"success":true}` and hands back the one that is there, with whatever it holds.
- **Copying a volume copies onto one that is there.** `POST /api/volumes/{name}/clone` into a name the host has a volume under answers `{"success":true}` and copies into it; onto itself it answers 500. It is not run as a job, whatever the caller says it accepts.
- **Looking into a volume there is none of makes it.** `GET /api/volumes/{name}/browse` for a name the host has no volume under answers 200 with no entries, and the host then has an empty volume by that name: the helper container was started with it mounted, and Docker makes a volume it is asked to mount.
- **A path can climb out of the volume into the helper.** `GET /api/volumes/{name}/browse?path=/../..` lists the helper container's own root, and `browse/content` reads its files. It is the helper's filesystem and not the host's, so nothing of the host is shown, but the path is not held to the volume.
- **A file asked for as a directory is answered alone**, as one entry named by where the helper has it, `/volume/note.txt`. A directory asked for as a file answers 400, a file over 1 MB 413, and a file that is not text is handed over as text all the same, with what could not be read as U+FFFD.
- **The helper stays until it is released.** It is one container per volume, on the host, from the first look until `POST /api/volumes/{name}/browse/release`, which answers success whether or not there was one.
- **A volume is written out through a helper container.** `GET /api/volumes/{name}/export` answers a tar of everything under a folder named `volume`, a `tar.gz` when `format` says so, a part of it with `path`, and one file as itself with `format=raw`; a form it does not know is a plain tar, and a path nothing is at a 500. Each export leaves a container named `dockhand-browse-` and the volume on the host, with the volume mounted, until `POST /api/volumes/{name}/browse/release` is called.
- **A helper is said to be released before it is gone.** The release answers `success` at once and the containers go a moment later; until they have, Docker will not remove the volume.
- **Asked to export a volume there is none of, Dockhand makes it.** The answer is a 200 with an archive of an empty folder, and the host has a volume of that name afterwards.

### Networks

- **A network's own list of who is on it is not the whole of it.** `containers` in `GET /api/networks` and in Docker's record of one network name the containers Docker has an end of the network for, which is the running ones and, for some networks, stopped ones it still knows the network's id for. A container put on a network while it was stopped is in neither. Each container's own record under `networks` in `GET /api/containers` names every network it is on, which is what the tools read.
- **A container is put on a network by its id.** `POST /api/networks/{id}/connect` with `containerName` alone answers 400 `Container ID is required`.
- **Docker removes a network that only stopped containers are on**, by `DELETE /api/networks/{id}` and by a prune alike: it refuses only for a running container (`has active endpoints`). The stopped containers then fail to start, `network <id> not found`, and making a network again by the same name does not mend it, since they hold the old one's id.
- **A network that is not there is a 500**, to a read and to a removal, where a volume is a 404. Docker's own three answer 500 `pre-defined network` to a removal.
- **An address range is given in lower case**: `ipam.config` takes `subnet` and `gateway`; spelled as Docker spells them they are ignored and Docker picks a range.

### Jobs

- **Slow work can be had as a job.** Pulling an image, pushing one, pruning images, scanning one image or all of an environment's, making a stack, saving a stack's compose file with a restart, the five stack actions, deploying a git stack with its progress, running a backup, restoring one, and a destination's upkeep and verify answer `{"jobId"}` at once to a caller that does not ask for JSON alone (see the stack actions above for what that means), and the work goes on in the background. The client asks for a job by giving the call the option `Accept: dockhand.AcceptJob`, which the `dockhand-job-accept` workaround adds to the seventeen of them.
- **`GET /api/jobs/{id}` says how it goes**: `status` is `running`, then `done`, or `error` for a job that did not do what it was for; `lines` are what it has reported, each an `event` (`progress`, and last of all `result`) with free-form `data`, which for a pull is Docker's own report of each layer and for a stack is what compose prints, a line at a time as `{"type":"line","line":"..."}`; and `result` is, once it has ended, the same answer the call gives a caller who waits. A job that failed has `{"success":false,"error":"..."}` for its result whatever the call's own answer looks like.
- **A job is its starter's.** Dockhand shows a job to the user who started it and to an administrator, keeps it for a while after it ends, and answers 404 `Job not found` for any other.
- **Stopping a job is a request.** `DELETE /api/jobs/{id}` answers `{"cancelled":true}` for a job that is running and `{"cancelled":false}`, with a 200, for one that has ended. A pull asked to stop ran to its end all the same, each time it was tried, and ended `done` with the image on the host.
- **Stack actions are done side by side.** Stopping a stack of two containers that each take four seconds to stop takes four seconds, not eight, so the wait is the slowest container's and does not grow with the stack.

### What is switched off

- **Features a server has not been set up for answer 404 `Not found`**, in text, to every call of theirs: the backup calls (which want `FEAT_BACKUPS_ENABLED=true` in the server's environment, as the changelog it serves at `/api/changelog` says of them: a beta), `/api/docs` (the API document again, which its own description says wants `FEAT_API_DOCS=true`) and `/metrics` (which wants `EXPORT_METRICS=true`).
- **Features of the Enterprise edition answer 403**, `{"error":"Enterprise license required","status":403}`: the audit log.
