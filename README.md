An [MCP](https://modelcontextprotocol.io) server, CLI and Go SDK for [Dockhand](https://dockhand.pro): **see every container on every Docker host a Dockhand manages, find the ones that are not right, read their logs and restart them** - from Claude Code, Claude Desktop, or any other MCP client.

A Dockhand already knows every host: the one it runs on, the ones it reaches at an address, and the ones behind a Hawser agent. dockhand-mcp asks it, so a model does not need a login on each machine, a Docker socket, or to know which host a container is on. "Is anything unhealthy anywhere?" is one call. "Why does it keep restarting?" is two more.

### What is in the box

- **Every host at once.** A read asks every environment unless one is named and sets the answers side by side, with a host that could not be asked named beside the ones that answered. A container is found by its name alone when only one host has it.
- **What is wrong, said.** A container that is unhealthy, that Docker keeps starting again, or that exited with an error says so in a word, and `problems` narrows a list to those. `container_get` gives what the health check printed and whether the host killed the container for memory.
- **Secrets stay hidden.** A container's variables, its command line and its log lines are read with passwords, tokens and keys hidden, told by the names beside them, unless a call asks for them.
- **Reads until told otherwise.** Every tool only reads unless `--enable-write` is given. The tools that change something take `dry_run`, say what they did in words, and read the result back from the host rather than trusting the answer to the change.
- **A Go SDK.** `sdk/dockhand` is a client for every call the Dockhand API has, 395 of them, generated from Dockhand's own description of itself, with no knowledge of MCP.
- **Tested against a real server.** Every tool and every read of the client runs against an actual Dockhand in Docker, with a Docker host on its socket and a second behind a real Hawser agent, both with its login off and with it on. The suites fail if a registered tool was never seen to answer.

The tools are about which hosts a Dockhand manages and everything Docker holds on them: adding and removing a host; containers, from making one to its files and keeping it on a current image; compose stacks; images, volumes and networks; and, of Dockhand's own side, what it does by itself, the registries it keeps, who it tells when something happens, what its scans find wrong in the images, who may sign in, its settings, its templates and config sets, the tags, labels and icons it keeps, what its web interface remembers, the secret stores it loads a stack's secrets from, and the git repositories it deploys stacks from. The rest of its own side, its backups, is in the SDK and has no tools yet.

## Installation

```bash
go install github.com/katbyte/dockhand-mcp@latest
```

Written against Dockhand 1.0.51.

## Configuration

All options can be passed as command-line flags, environment variables, or via a configuration file.

| Variable | Flag | Description |
|---|---|---|
| `DOCKHAND_SERVER` | `--server`, `-s` | the address the Dockhand web console answers on, e.g. `http://dockhand:3000` |
| `DOCKHAND_TOKEN` | `--token`, `-t` | a Dockhand API token (web console, Profile, API tokens); leave it out for a Dockhand with its login switched off, which takes none |
| `DOCKHAND_ENABLE_WRITE` | `--enable-write` | register the tools that change something; without it every tool only reads |
| `DOCKHAND_ENABLE_DELETE` | `--enable-delete` | register the tools that delete as well; needs `--enable-write` |
| `DOCKHAND_READ_ONLY` | `--read-only` | register only tools that never change anything: the default, said out loud, and refused beside `--enable-write` |
| `DOCKHAND_TOOLSETS` | `--toolsets` | groups of tools to register, default `core`: `all`, `core`, `manage`, `containers`, `files`, `updates`, `stacks`, `resources`, `setup`, `schedules`, `registries`, `notifications`, `vulnerabilities`, or a resource family like `container` (`core` is always included) |
| `DOCKHAND_ALLOW_TOOLS` | `--allow-tools` | register these tools as well as the toolsets asked for, or only these when no toolset is (names, `container_*` globs, or `essential`) |
| `DOCKHAND_DENY_TOOLS` | `--deny-tools` | never register these tools, whatever asked for them (names or globs such as `*_stop`) |
| `DOCKHAND_LOG` | | log level (`WARN` default; `DEBUG`, `TRACE`, ...) |
| `DOCKHAND_LISTEN` | `--listen` | serve MCP over HTTP on this address (e.g. `:8080`) instead of stdio |
| `DOCKHAND_AUTH_TOKEN` | `--auth-token` | bearer token required on the HTTP endpoint (required with `--listen`) |
| `DOCKHAND_ALLOW_NO_AUTH` | `--allow-no-auth` | serve HTTP with no bearer token at all: anyone who can reach the port can use every tool |

An API token acts as the Dockhand user who made it, and may do what that user may. A Dockhand with its login switched off asks nobody who they are: anyone who can reach it can do everything it can, through these tools or without them, and `server_info` says so.

### Configuration File

You can place a `.dockhand-mcp` file in your home directory `~/.dockhand-mcp` (for global settings) and in your current directory `./.dockhand-mcp` (for per-project settings). Both are read, the project's over the home one, so a project file only needs the settings it changes. Keys are the environment variable names, with or without the `DOCKHAND_` prefix, in `env` format:

```env
SERVER=http://dockhand:3000
TOKEN=dh_...
ENABLE_WRITE=true
```

A flag or an environment variable beats either file.

## Usage

Quick connectivity check:

```bash
dockhand-mcp info
```

### Register with Claude Code

`.mcp.json`:

```json
{
  "mcpServers": {
    "dockhand": {
      "command": "dockhand-mcp",
      "args": ["serve"],
      "env": {
        "DOCKHAND_SERVER": "http://dockhand:3000",
        "DOCKHAND_TOKEN": "..."
      }
    }
  }
}
```

Or from the shell:

```bash
claude mcp add dockhand -e DOCKHAND_SERVER=http://dockhand:3000 -e DOCKHAND_TOKEN=... -- dockhand-mcp serve
```

### Run as a service (HTTP transport)

`serve --listen :8080` serves the MCP Streamable HTTP transport at `/mcp` (plus `GET /healthz`) instead of stdio. `DOCKHAND_AUTH_TOKEN` is required: clients must send `Authorization: Bearer <token>`, and the server refuses to start without one unless `DOCKHAND_ALLOW_NO_AUTH=true` says that anyone who can reach the port may use every tool. Register it from any machine:

```bash
claude mcp add --transport http dockhand http://dockhand-mcp:8080/mcp \
  --header "Authorization: Bearer $DOCKHAND_AUTH_TOKEN"
```

### Docker

Releases publish a multi-arch (amd64, arm64) image to `ghcr.io/katbyte/dockhand-mcp`, tagged `vX.Y.Z`, `vX.Y` and `latest`. `docker-compose.yml` is the default always-on deployment: it runs that image and reads secrets from a gitignored `.env` (copy `.env.example`). Adjust `DOCKHAND_SERVER` and `TZ` in the compose file, then:

```bash
cp .env.example .env      # fill in DOCKHAND_TOKEN and DOCKHAND_AUTH_TOKEN
docker compose up -d
```

`make docker` builds the same image from source, tagged `dockhand-mcp`, with version info from git. The image is alpine-based (so `docker exec -it dockhand-mcp sh` works), runs as a non-root user and has a healthcheck against `/healthz`. The binary is the entrypoint, so `docker run --rm ghcr.io/katbyte/dockhand-mcp info` works as a connectivity check with the `DOCKHAND_*` variables passed via `-e`.

The tools that change something are only registered when `--enable-write` / `DOCKHAND_ENABLE_WRITE` is set: the starts, stops and restarts, `env_create`, `env_edit`, `env_schedules`, `agent_token_create`, `server_mkdir`, `schedule_run`, `schedule_set`, `registry_create`, `registry_edit`, `image_push`, `notification_test`, `notification_create`, `notification_edit`, `notification_link`, `scanner_set`, `image_scan`, `image_scan_all`, `user_create`, `user_edit`, `login_set`, `sso_create`, `sso_edit`, `settings_set`, `preferences_set`, `favorite_set`, `secret_provider_create`, `secret_provider_edit`, `git_credential_create`, `git_credential_edit`, `git_repository_create`, `git_repository_edit`, `git_stack_create`, `git_stack_edit`, `git_stack_sync`, `git_stack_deploy`, `template_source_create`, `template_source_edit`, `config_set_create`, `config_set_edit`, `tag_create`, `tag_edit`, `tag_assign`, `label_edit`, `label_assign`, `icon_set`, `container_create`, `container_edit`, `container_limits`, `container_update`, `container_pause`, `container_unpause`, `container_rename`, `container_exec`, `container_autoupdate_set`, `container_updates_clear`, the `container_file_` tools that write, send, make, move and set permissions, `image_pull`, `image_tag`, `image_load`, `volume_create`, `volume_clone`, `volume_export`, `network_create`, `network_connect`, `network_disconnect`, `stack_create`, `stack_edit`, `stack_deploy`, `stack_down`, `stack_adopt`, `stack_move` and `job_cancel`. Each that makes a change takes `dry_run`, but for `login_set`, which asks for `confirm` before it switches the login on or off. The tools that remove something, `env_delete`, `container_events_clear`, `scanner_cache_clear` and every `_delete` and `_prune`, are only registered when `--enable-delete` / `DOCKHAND_ENABLE_DELETE` is set as well; without `confirm` each says what would go and removes nothing.

**Two tools that only look need `--enable-write` all the same.** Docker has no way to see inside a volume, so for `volume_files` and `volume_read` Dockhand starts a small helper container on the host with the volume mounted, and the first time it has the host pull the `busybox` image for it. Nothing in the volume is changed and the helper is taken away after each look, but a session that was told it may only read should not be making a host pull and run things, so these two wait for the switch.

**A prune says what it would take before it takes it, and one of them is refused outright.** Docker prunes a network that no *running* container is on, so a stack that is merely stopped loses its networks and then will not start, failing with `network not found`. `network_prune` lists the stopped containers a prune would leave stranded and refuses to go on unless `stranding` is given; `network_delete` refuses a network any container is on, stopped or not. `volume_prune` removes named volumes too, where `docker volume prune` leaves them, so its list is worth reading: it is the data of whatever is no longer there to mount it.

**Changing what a container was made with makes it again.** Docker cannot change a container's variables, ports, mounts or image once it exists, so `container_edit` and `container_update` have Dockhand stop it, remove it and make it again under the same name with the change, keeping everything not named: its networks, restart policy, limits and the rest. It is started again when it was running, and what it wrote inside itself, outside its volumes, is gone. `container_limits` is the exception: memory, processors and the restart policy are set on the container as it runs. A container that is Dockhand itself, or one of its agents, is refused by both: making it again through Dockhand stops the thing doing the work part way.

**An update is a pull first, and nothing more when the pull brings nothing.** `container_updates` says which containers have something newer to be had: another image under the very tag they run, and, when Dockhand is set to look for them, a newer version tag. `container_update` pulls the image and only makes the container again when what came is another image than it runs, so asking twice does no harm. `container_autoupdate_set` has Dockhand do the same by itself on a schedule, with nobody asked, which is right for something that should follow its tag and wrong for anything that must not restart unwatched.

**A file written into a container is checked before it is written.** Dockhand writes a file wherever it is told, and told to write one where a directory is, it puts the file in the directory's place and everything in the directory is gone. `container_file_write`, `container_file_move` and `container_file_upload` look at the path first: a directory is always refused, and anything else that is there is replaced only with `overwrite`. `container_file_delete` removes as `rm -rf` does, so it says what is there before it removes it, and refuses the container's root, a directory directly under it and the place a volume is mounted. A file written or sent in is root's afterwards, whatever it replaced, and `container_file_perms` gives it back. Writing, sending and fetching work on a stopped container too, which is how one that will not start for a bad file is mended; the rest run a command in the container and need it running.

**What Dockhand does for a host unasked is set in one place, and said plainly.** `env_get` shows a host's schedules beside the machine itself, and `env_schedules` sets them: when the registries are asked whether its containers are behind, when its images are pruned, when a filling disk is warned of. Two of them act on a whole host with nobody watching: `auto_update` pulls newer images and makes containers again on the schedule, and a scheduled prune of `all` removes every image nothing is using at that moment, a stopped stack's among them. Dockhand saves a schedule whatever its time says, and one it cannot read never runs, so a time that is not five cron fields is refused here. `env_edit` changes how a host is reached, and has Dockhand try the new way at once: a host that is no longer reached is one whose containers cannot be seen until it is put right.

**A host Dockhand cannot reach is added as one whose agent calls in.** `env_create` with `connection: hawser-edge` saves the host with nothing to try and answers the token its Hawser agent is to call in with, once; `agent_list` then says which agents are connected and which hosts are still waited for. A host has one token that works: `agent_token_create` replaces it and `agent_token_delete` revokes it, and either cuts off the agent that was connected. One thing Dockhand does here costs five minutes when it is not known: an agent that calls with a token Dockhand does not take is turned away, and so is every call from that agent's address for the five minutes after, the right token's among them. So stop an agent before its token is replaced; the tools say so before they do it.

**A registry's login is kept by Dockhand, and used for the hosts.** A host pulling an image whose name leads with a kept registry's address is signed in with what Dockhand keeps for it, and so is a push: `image_push` sends an image that is on one host to a registry, from where `image_pull` brings it to the others. `registry_create` and `registry_edit` try the registry and say whether Dockhand can use it. Two things a registry does are said before they bite: deleting one tag deletes every other tag of that image holding the very same contents, which `registry_image_delete` names once they are gone; and a registry that turns Dockhand's login away is reported as that, where Dockhand's own answer reads as if it had refused the caller.

**What Dockhand does with nobody asking is one list, and each run of it is kept.** `schedule_list` gives every schedule Dockhand keeps, whatever set it: a container kept on the newest image, a host's check for newer images, its image prune, a git stack's sync, a backup, and Dockhand's own tidying. `schedule_history` gives the runs, so `status: failed` is everything that went wrong overnight, and one run by its number comes with what it logged. A schedule is named by its type and its number together; the types are written with hyphens here (`container-update`, `image-prune`), since written Dockhand's way three of them are the names of tools. `schedule_run` does now what the schedule would do in its time, which for an update or a prune changes a host.

**Who hears of what is decided in two places, and the tools say which.** A channel is a way of telling people: mail, or an address of another service such as ntfy, Gotify, Discord, Slack, Telegram or a webhook. What happens on a host, a container dying or being updated, reaches a channel only through its tie to that host, which `notification_link` makes and which holds a list of events of its own; the channel's own list decides only the events of Dockhand itself. So a channel that is saved and tied to nothing is silent about every host, and `notification_create` says so. `notification_test` sends for real: through one channel, or by setting an event off for a host, which answers how many channels took it. An address is listed by its service and host alone, since the rest of it is the token that lets anyone send to it and Dockhand hands it back whole to whoever asks. And of Dockhand's own events only the one about its license can be set off for a test: the others it would send to nobody, so they are refused with the reason.

**A host that scans nothing is not a host with nothing wrong.** Dockhand scans images with grype or trivy, run as a container on the host that has the image, and a fresh Dockhand scans nothing anywhere. Asked to scan on a host set to scan with nothing, it answers that the scan is complete and found no vulnerabilities; `image_scan` and `image_scan_all` refuse instead, and `vulnerability_list` says for each host how many of its images were ever scanned, since an image never scanned has no findings. The list is the gravest first, counts every finding that matched, and narrows to what a newer version puts right, which is the list of what an update would mend. A scanner pulls its own image and downloads its database the first time, so a first scan takes a minute or more and comes back as a job when it outlasts the wait. Dockhand runs the scanners from Docker Hub unless told: `scanner_set` names another registry, for every host at once.

**Dockhand will lock itself if asked, and these tools will not ask.** Dockhand makes every user an administrator, and guards the last one only when it is the only user there is: with a second user of any kind it will switch off, unmark or remove the last administrator, and it will switch its login on over a server whose only user is switched off. Either can leave a Dockhand nobody can sign in to, with no call that undoes it. So `user_edit` and `user_delete` leave the last user that is both switched on and an administrator as it is, and `login_set` does not switch the login on unless such a user exists. Switching the login either way needs `confirm`, and without it the answer says what it would mean: off, anyone who can reach Dockhand's address has all of it and every host it manages; on, this server is let in only with an API token, which Dockhand lets nobody make except signed in to its web interface, so a server started with no token is turned away from that moment, and the answer says so (`turned_away`). `token_list` lists the tokens of the user this server signs in as, and no tool makes or revokes one. Taking the administrator's mark from a user holds it to nothing on a Dockhand with no licence, which `user_edit` says when it is asked to.

**Settings are checked before they are sent, because Dockhand checks nothing.** `settings_get` lists every setting of Dockhand itself by the name its API gives it, the ones that say which newer versions of an image it notes among them (`semver.*`), and `settings_set` changes the ones named. Dockhand saves a schedule it cannot read, after which that clean-up job never runs, and saves a time zone it does not know while answering that the save failed; it raises a number it finds too small and passes over a word it does not know, each without a word. So a schedule and a time zone are checked first, every setting is read back, and one Dockhand did not take as given is put back to what it was and named in `not_taken`: a setting ends as it was asked for or as it was. A Retention setting is what the clean-up jobs say they go by, so a smaller one has the next run remove more.

**A template is a starting point, and the tools say where it falls short.** Dockhand has about a thousand app templates as it comes, fetched from lists that others keep: `template_list` searches them and `template_get` gives one in full with the compose file Dockhand writes for it, which is text to read, change and make a stack from. Nothing is started by either. Dockhand writes `undefined` where a template names no place on the host for a volume, which is no volume, and `template_get` says so when it has. A stack template's compose file is fetched from its makers' repository, and the tool says which when that cannot be reached. Dockhand takes any address as a source of templates and says nothing when it answers nothing readable, so `template_source_create` and `template_source_list` count what came of each; it removes one of the sources it comes with as readily as any other, and nothing brings it back as its own, which `template_source_delete` says before it does. What Dockhand fetched from an address it keeps for an hour, with the name the source had then.

**A tag belongs to a name, not to the thing that has it.** Dockhand keeps the tags of a container and of a stack under its name on one host: a container that is renamed leaves its tags behind under the name it had, a container or a stack that is removed leaves them too, and whatever next has that name has them. `tag_list` gives each tag with the names it is on, and `tag_assign` refuses to tag a name nothing has, which Dockhand would do without a word, while letting what a name still holds be taken from it. It refuses a tag there is none of as well: Dockhand answers that with an error only after it has taken away every tag the name had, and should Dockhand refuse a change all the same, `tag_assign` puts back what was there. A tag is one of sixteen colours, and `tag_create` and `tag_edit` refuse any other, which Dockhand would make slate or quietly keep as it was.

**The labels of hosts are plain words, and Dockhand is careless with them.** `prod` and `Prod` are two labels. Asked to rename a label to the name it already has, Dockhand takes it from every host, so `label_edit` never sends that. Given a colour that is not `#` and six hexadecimal digits, Dockhand answers that it was set and takes away the colour the label had, so one is checked first. Renaming a label to the name of another makes the two one for good, and waits for `merge`. Given a label for a host it does not manage, Dockhand passes over it without a word, so `label_assign` refuses one.

**What the web interface remembers is partly one user's and partly everyone's.** `preferences_get` reads it and `preferences_set` changes it: the order hosts and tags are listed in, the sidebar, the columns of a grid and whether the schedules page hides Dockhand's own jobs are each user's own, here the user this server signs in as, while the dashboard with its tiles and the pages the interface opens on are everyone's. Dockhand saves an order or a tile that names a host or a tag there is none of, and any text as a layout, so those are looked up and checked first; a tag that is removed stays in the order it was saved in, and is shown by its number. The pages a user chose for themselves, and their theme and fonts, are kept with their profile, which only a browser that signed in may read or set.

**The favourites of a log view are one list, and Dockhand's own reordering loses half of it.** For each host Dockhand keeps the containers whose logs are at hand and the groups whose logs are read together in a single list, and asked to reorder the containers it drops every group, and asked to reorder the groups, every container. `favorite_set` therefore takes the whole list, in order, and writes it as one, and `favorite_list` reads it. A favourite is kept by a container's name and outlasts the container; a name no container has is refused unless it is kept already, since Dockhand keeps any text.

**An image and a volume can be carried as files.** `image_export` writes an image to a tar archive on the machine this server runs on, under whichever of its names is asked for, and `image_load` puts one on a host from such an archive: how an image reaches a host that cannot pull it. Dockhand loads only onto a host it reaches itself, and refuses one behind an agent. `volume_export` writes what a volume holds, or one folder of it, the same way. None of them ever writes over a file that is there. Two things Dockhand does are kept from biting: asked to export a volume there is none of, it makes the volume and answers an empty archive, so a volume is looked up first; and it says the helper container it read a volume through is gone before it is, which keeps the volume from being removed, so the volume tools wait until it really is.

**A stack's secrets can be loaded from a secret store rather than kept by Dockhand.** A secret provider is a store outside Dockhand - a Vault, or anything that speaks its API, among the kinds it knows - and a stack given one, with a path in it, gets every key at that path as a variable each time it is deployed, so the values are in no file. `secret_provider_keys` lists the names at a path, never the values, and `stack_create` and `stack_edit` take `secret_provider` and `secret_path`, asking the provider first whether anything is there. Dockhand is careless at three points, each of which the tools check: it saves a provider it cannot reach, and a stack bound to one is then not deployed, so a provider is tried first and `stack_deploy` says when a failed deploy has one behind it; it keeps the token when a provider's address is changed and sends it to the new address, so `secret_provider_edit` moves one only with its token given again; and it removes a provider that stacks use without a word, after which their next deploy succeeds with every such variable empty, so `secret_provider_delete` names those stacks and waits for `even_used`.

**A stack can be deployed from a git repository, and then its files are the repository's.** A git stack is a compose stack Dockhand fetches from a repository it keeps and copies into place at each deploy: `git_stack_create` makes one from a repository and a branch, with the variables and secrets Dockhand is to keep for it besides, and `git_stack_deploy` fetches and brings it up. It can be fetched by itself on a schedule, or when a git server calls its webhook, which takes the webhook's secret and no login. Since each deploy replaces the stack's files, `stack_edit` refuses a git stack and `git_stack_edit` changes what Dockhand keeps for it. Dockhand is careless at six points, each of which the tools check. It gives the webhook's secret back to whoever reads the stack, so `git_stack_get` hides it unless asked; and the call that deploys and waits answers the values of the stack's secrets with how it went, so the tools use the other one. It saves a repository it cannot fetch and a branch that is not there, and says so only at the next deploy, so both are tried first. A fetch alone marks a commit as seen, after which the schedule and the webhook find nothing new and never deploy it: `git_stack_sync` says so, and `git_stack_get` tells the commit fetched from the one that runs. It renames a stack that is running and leaves its containers behind under the old name, and a rename it refuses because the name is taken is half done all the same, after which the next rename takes the other stack's variables and secret provider: `git_stack_edit` renames only a stack that is down, to a name nothing has. And it removes a credential repositories are fetched with, and a repository git stacks are made from, without a word, the second taking those git stacks with it and leaving their containers running: `git_credential_delete` and `git_repository_delete` name what uses each and wait for `even_used`. A repository's own fetch, deploy and webhook are leftovers with no tool: they act on a copy no git stack uses, and that deploy runs compose on the Docker that Dockhand itself is on.

**A config set is only kept.** It is a bundle of settings for a container - variables, labels, published ports, mounts, a network mode and a restart policy - and nothing in Dockhand's API applies one: `config_set_list` gives a set in the words `container_create` takes, to be handed to it. Dockhand checks nothing of a set but its name, so `config_set_create` and `config_set_edit` check its ports, mounts, names and restart policy first. A value whose name says it is a secret is hidden unless `reveal_secrets` is given, and `config_set_edit` changes a variable at a time, so that one that is hidden need not be known to be kept.

**An icon is a small thing that Dockhand keeps carelessly.** `icon_set` gives a container, a stack or a host an icon: one of Dockhand's own by name, one of selfh.st's as `icon_search` finds them, or a picture sent from this machine, which `icon_download` fetches back. Dockhand saves any text as a name and, for a host, any file as a picture, so both are checked first. A container's and a stack's icon is kept under its name, as tags are, and Dockhand keeps one for a name nothing has; for a stack it then lists a stack of that name with nothing in it, so a name that is no container's or stack's is refused. And giving an icon to a stack Dockhand only found makes it keep a record of that stack for good, after which Dockhand's own adoption makes a second stack of the file: `icon_set` wants `even_found` for that, and `stack_adopt` gives such a stack its file another way.

**Slow work does not hold a session up.** Dockhand runs a pull, a prune, a deploy or a down in the background, and a tool that starts one waits for it only so long: 50 seconds unless `wait` says otherwise, 300 at most. Done by then, the answer is what was done, read back from the host. Still going, the answer says so and gives a job id, and `job_get` says how it is going and, in the end, how it went.

**A stack is either one Dockhand has the compose file of, or one it only found.** A stack someone brought up on a host with `docker compose` shows up in Dockhand all the same, and Dockhand can start, stop and restart its containers, but it has no file for it: `stack_get` says `kept: found` and where the host says the stack came from, and `stack_deploy`, `stack_edit` and `stack_move` refuse it. `stack_adopt` gives Dockhand the file where it lies, which has to be a path Dockhand's own container can see; nothing running is touched, and from then on the stack is deployed from that file. It is not undone lightly: Dockhand cannot be made to forget a stack again without removing its containers. A stack Dockhand only found that was then given an icon is one it keeps a record of, with still no file: `stack_get` says `kept: external`, and it is adopted and removed as a found one is.

**Three things Dockhand does without a word are refused here unless asked for.** Making a stack under a name that is taken replaces the file Dockhand has for that name, or takes over a stack it only found, so `stack_create` refuses a name any stack on the host has. Moving a stack's files into a folder that is already there writes over files of the same name in it, so `stack_move` refuses one unless `overwrite` is given. And a compose file that does not parse is saved as it is, and is then a stack that cannot be deployed or, unforced, removed, so `stack_create` and `stack_edit` run Dockhand's own check first and refuse a file compose would not take.

**Removing a stack removes its containers, running or not.** For a stack Dockhand keeps in its own data directory the files go too, unless `keep_files` is given; files outside it, of a stack that was adopted or moved, are never deleted. Named volumes stay unless `volumes` is given. For a stack Dockhand only found, the containers are all that goes. `stack_down` is the gentler one: the containers and the networks go, the file and the variables stay, and `stack_deploy` brings it back; its `remove_volumes` deletes data and so needs `--enable-delete` as well.

`dockhand-mcp tools` prints what the current flags would register, grouped by toolset, and needs no server:

```sh
dockhand-mcp tools                               # the default set
dockhand-mcp tools --toolsets all --enable-write # every tool
dockhand-mcp tools -q                            # names only
```

### One tool more, or a few less

`--allow-tools` asks for tools by name, as `--toolsets` asks for them by set, and a session gets what either names: "these sets, and this tool as well". On its own, with no toolset beside it, it is only the tools it names. `--deny-tools` takes tools out of whatever was asked for, which is how a toolset is narrowed. Both take comma-separated tool names and globs with a leading or trailing `*`, and `--allow-tools` the `essential` preset. Neither lets a tool that changes something past `--enable-write`.

```sh
DOCKHAND_ALLOW_TOOLS=essential                                             # the four essential tools and nothing else
DOCKHAND_ENABLE_WRITE=true DOCKHAND_TOOLSETS=core DOCKHAND_ALLOW_TOOLS=container_restart   # core, and restarting a container as well
DOCKHAND_ENABLE_WRITE=true DOCKHAND_TOOLSETS=manage DOCKHAND_DENY_TOOLS=*_stop   # start and restart, never stop
```

### Finding what is not right

```text
container_list problems=true          every container that is unhealthy, restarting or exited with an error, on every host
container_get container=<name>        why: what its health check printed, its exit code, whether the host killed it for memory
container_logs container=<name>       what it wrote before it stopped
stack_logs stack=<name>               what its neighbours wrote around the same time
container_restart container=<name>    once the cause is dealt with
```

## Using the client on its own

`sdk/dockhand` is a plain Go client for the Dockhand API with no knowledge of MCP. It is generated by [pandorest](https://github.com/katbyte/pandorest) from the OpenAPI document every Dockhand serves about itself, and sends its requests through pandorest's base client, which is built on [go-kt's HTTP package](https://github.com/katbyte/go-kt/tree/main/chttp). If you only want to talk to Dockhand from Go, take it and ignore the rest:

```go
import "github.com/katbyte/dockhand-mcp/sdk/dockhand"

client, err := dockhand.New("http://dockhand:3000", os.Getenv("DOCKHAND_TOKEN"))
environments, err := client.GetEnvironments(ctx)
containers, err := client.GetContainers(ctx, dockhand.GetContainersOperationOptions{Env: &environments.Model[0].Id})
```

`dockhand.NewWithoutLogin` makes a client for a Dockhand with its login switched off. A read is asked for again when a gateway could not reach the server (502, 503, 504) or the connection dropped, three times in all; a write is sent once; a redirect is refused rather than followed. It logs nothing unless handed a logger with `client.WithLog`, and then traces every request and answer with tokens, passwords and keys blanked: dockhand-mcp hands it its own, so `DOCKHAND_LOG=trace` shows the traffic. A status a call does not document is a `*client.StatusError` carrying what Dockhand said; `client.IsNotFound`, `IsUnauthorized` and `IsForbidden` read the common ones.

It has a method for **every one of the 395 operations** in Dockhand's document, named for its method and path: `GET /api/stacks/{name}/compose` is `GetStacksByNameCompose`. `make apicheck` fails if one is missing, so the claim is checked rather than asserted.

That document comes from Dockhand itself: every Dockhand server serves a description of its own API at `/openapi.json`, and `api-defs/get.sh` starts a throwaway server of the published image, asks it for that, and removes it again. Nothing is taken from Dockhand's source repository. The document is Dockhand's own, so it is not kept in this repository: what is committed is a pin (the version, the image and a checksum of the document's content), the definitions imported from the document, and the client generated from those. A document whose checksum is not the pinned one is refused, and `make` fetches it before anything reads it.

Dockhand writes that document from its own code, and what a call answers is the part it gets least right: a quarter of the calls say nothing of their answer and others declare a fraction of it. Each such fault that has been found is fixed with a named workaround (`sdk/pandorest/workarounds`), proved against a running server, and written up in [api-defs/README.md](api-defs/README.md) beside what the server does that no document says. An answer no workaround has given a shape yet is handed back as raw JSON.

Each suite runs twice on the same server, because a Dockhand is run two ways: open, as it comes, with no login; and with its login on, which the suite switches on itself, through the client, making the first user and minting the API token it then asks with.

The read sweep (`integration/sweep_test.go`, pandorest's) calls every `GET` the API has against the server and holds each answer to decoding into its model with something in it. A read that cannot simply answer has a case that says why (`integration/sweep_cases_test.go`): a stream of events that never ends, a feature of Dockhand's paid edition, something a server as it comes has none of. A case whose call starts answering fails the sweep, so the list cannot go stale.

The journeys (`acceptance/journey_test.go`) chain the tools the way a session does. The first is the suite's own setup: a Dockhand that manages nothing takes on its two hosts through `env_test` and `env_create`, one by its socket and one through its agent.
